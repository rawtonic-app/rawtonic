# Recipe schema
Managed storage uses a versioned envelope, never unversioned loose parameters:
```json
{"schema_version":1,"process_version":"rapidraw-1.6.4","adjustments":{},"layers":[],"snapshot":null}
```
The inherited adjustment schema is defined by `src/utils/adjustments.ts` defaults and UI slider bounds; the adapter preserves fields losslessly. `adjustments` contains the native renderer recipe, including inherited masks/crop/retouch vectors. `layers` is reserved for the future independent composite model and must remain empty until implemented, rather than being silently ignored. Each history step is immutable in SQLite, with a version head pointer; undo/redo changes the head. Metadata is shared between versions.
Known fields: exposure -5..5 EV, contrast/highlights/shadows/whites/blacks -100..100, saturation/vibrance -100..100; exact inherited defaults must be checked before conversion. These are target semantic ranges, not a statement that upstream scale matches. Do not translate without an explicit process migration.
Forward versions are rejected for editing. Unknown adjustment fields are retained. Raster mask paths must be relative to the session and accompanied by hashes before portable package export. Validation and a complete machine-readable schema are outstanding.
`adjustments.sectionVisibility` switches parts of the recipe off without losing their values. Inherited master keys: `basic` (exposure, contrast, brightness, highlights, shadows, whites, blacks), `color` (white balance, saturation, vibrance, hue, colour grading, colour mixer, calibration), `curves`, `details` (sharpening, noise reduction, clarity, structure, dehaze), `effects`. Per-tool keys (2026-10-03, Lightroom's panel eye) narrow these further: `whiteBalance` (temperature, tint), `presence` (clarity, structure, dehaze, vibrance, saturation), `colorMixer` (hsl), `sharpening` (sharpness, sharpnessThreshold), `noiseReduction` (luma and colour noise reduction). A parameter renders only if its master and its tool key are not `false`; a missing key means on.

`adjustments.guidedPerspective` holds the guided perspective: `lines` (up to two `vertical` and two `horizontal` guides, coordinates 0–1 of the uncropped photo), `enabled` (two or more lines), `upright` (2026-10-04: `off`, `auto`, `level`, `vertical`, `full` or `guided`; missing on recipes from before Upright) and `autoCrop`. With `upright` set to anything but `off`, the correction zooms until no empty corners remain (Lightroom's Constrain crop) unless `autoCrop` is `false`; recipes without `upright` never zoom.

`adjustments.baseCurve` (2026-10-04): `"standard"` (missing key), `"highContrast"`, `"extraShadow"`, `"linear"`. RAW files only. Other names render with the standard curve. The curve choices are applied after the base look as a change of display luminance and chroma by display level: High contrast darkens the shadows and brightens the upper midtones around mid grey, Extra shadow lifts the shadows by up to 0.8 EV, Linear response undoes the default tone curve (Rawtonic's own shapes since 2026-10-11). Part of the copy/paste group with Exposure and the tone mapper.

`adjustments.grainStructure` (2026-10-12): `"even"` (missing key, the original grain), `"soft"`, `"clumped"`, `"speckled"`, `"gritty"`. Unknown names render as `"even"`, so recipes without the key export byte-identically to before (the renderer, CLI and headless export never default to anything else). The editor writes the key: grain turned on in a recipe without one gets `"clumped"` (new edits, and grain turned on again after resetting the grain tool, which removes the key); a recipe loaded with grain but without the key gets `"even"` written, so its grain keeps rendering Even when copied, pasted, synced, saved as a preset or turned off and on; presets and pasted settings from before the choice with grain but no key are applied as `"even"`. Lightroom presets, XMP and catalog imports with grain got `"clumped"` until 2026-10-27; since then they get film grain (`grainVersion` 3), which has no structure. Amount, Size and Roughness work for every structure and each is scaled to Even's strength at Roughness 50 (Gritty 1.4×). Even and Clumped are equally strong in every tone (Clumped: Roughness gathers fine grain into clumps); Soft (rounded grain with irregular clusters), Speckled (bright specks over a fine grain) and Gritty (coarse, hard-edged grain) are strongest around display level 0.45 and fade towards black and white. Capture One styles with grain mapped `FilmGrainType` onto it until 2026-10-27 (Fine or none → even, Silver Rich/Soft/Cubic → soft, Tabular → speckled, Harsh → gritty); since then onto film grain (`grainVersion` below). Part of the grain copy/paste group.

`adjustments.grainVersion` (2026-10-23, `crates/engine/src/image_processing.rs` `GRAIN_VERSION`, shader `apply_portable_grain`): which grain `grainAmount`, `grainSize`, `grainRoughness` and `grainStructure` render. `2`: the portable grain — the same gradient noise, structures, strength and tone masks as `1`, but the lattice cell and the position in it are computed exactly in integers (12 fractional bits, the frequency by integer long division) and the gradients come from an integer hash (PCG), so every GPU renders the same grain pattern (within float rounding of the interpolation); statistically the same grain, measured 2026-10-23 on a Nikon D7200 NEF export (grain = render − the render without grain, luma in 8-bit levels, mid-tones): standard deviation version 2 / version 1 = 1.000–1.001 at Amount 25/50/100 (Size 25, Roughness 50), Size 0/50/100, Roughness 0/100 and the Soft, Clumped, Speckled and Gritty structures (e.g. Amount 50: 7.66 vs 7.65), spectral centroid within ±0.002 cycles/px (0.068–0.383), share of power below 0.05 cycles/px, skewness and kurtosis equal within ±0.02 (Speckled +0.64 / +1.40 vs +0.64 / +1.38); a noise-only comparison of both versions over all structures × Size 0/25/50/100 × Roughness 0/50/100 on a 1024² window gave std ratios 0.985–1.010 (within that window's sampling noise). Unverified: other cameras and image sizes beyond one 24 MP photo, and the running app side by side. Size is clamped to slider 5–200. `1`: the earlier grain, whose float hash turned one-ulp differences between GPUs into a different pattern (an AMD and an NVIDIA GPU differed on ~90 % of the pixels). Without the key a recipe renders with `1`; the editor writes `2` when grain is turned on in a recipe without the key, writes `1` into a loaded recipe, preset or pasted settings with grain but without the key (in Copy/Sync it is a processing version: the destination keeps its own unless the processing versions are chosen), removes the key with the Effects tool's reset, and copies it with the grain values (the source's, else `1` for a source with grain, `2` for one without); Lightroom and Capture One imports with grain got `2` until 2026-10-27 and get `3` since (see below). A value above the newest renders as the newest. `3` (2026-10-27, `crates/engine/src/film_grain.rs`, shader `apply_film_grain`): film grain — grains as disks with random radii in each dye layer of a negative (a Boolean model), the layer's density level taken from the pixel through a logistic print response, the grain read over each pixel's footprint from a precomputed tile (so a smaller render shows the full-size grain scaled down: a render at 1/2–1/8 size keeps 91–97 % of the box-scaled full-size grain's standard deviation, Metal 2026-10-27; the Develop view's Fit preview, rendered below its display resolution and then scaled, shows about 25 % more grain than the export seen at that size), changing the negative's density and printed back; strongest in the midtones. `grainStructure` does not apply; `grainColor` (0–100, missing = 0) sets how independent the three dye layers' grain is (0: one neutral layer like black-and-white film). The editor writes `3` into new edits; old recipes keep their version and render byte-identically. Lightroom imports with grain get `3` with Amount, Size and Roughness 1:1 and `grainColor` 0 (film grain's scales were calibrated on Lightroom's: Amount 50 / Size 25 / Roughness 50 = 8.66 vs 8.65 8-bit σ, spectral centroid 0.150 vs 0.147 cycles/px). Capture One styles and catalogs with grain get `3`, `grainColor` 0, and per `FilmGrainType` a Roughness and a Size interpolated linearly over `FilmGrainGranularity` 0 / 50 / 100, Amount = Impact × a strength factor (Fine 27, 5 / 5 / 5, ×0.63; Silver Rich 100, 7 / 17 / 21, ×0.36 / 0.60 / 1.25; Soft 100, 8 / 11 / 18, ×0.58 / 0.90 / 1.33; Cubic 99, 10 / 15 / 23, ×0.46 / 0.75 / 1.16; Tabular 11, 38 / 49 / 61, ×0.46 / 0.84 / 1.45; Harsh 0, 50 / 60 / 63, ×0.74 / 1.23 / 2.20), fitted so the spectrum (centroid, share below 0.05 cycles/px) and the midtone strength on a grey chart match Capture One 16's (`src-tauri/src/costyle.rs`). Not matched: Capture One's types are relatively stronger in the shadows and weaker in the highlights than film grain, and Tabular/Harsh have distribution shapes (bright specks, flat tops) film grain does not reproduce.

RAW detail defaults for recipes without the key (2026-10-04): `sharpness` 40, `colorNoiseReduction` 25, `lumaNoiseReduction` 15; JPEG/TIFF 0.

`adjustments.colorNoiseVersion` (2026-10-13, `crates/engine/src/color_noise.rs`): which colour noise reduction `colorNoiseReduction`, `colorNoiseDetail` and `colorNoiseSmoothness` drive. `2`: the multi-scale filter (chroma pyramid of five scales, each thresholded by the colour noise measured in the photo at that scale and brightness; luminance and colour edges protected; its output changed on 2026-10-14 before any release, with the brightness noise profile and refitted guards, Detail and Smoothness, and again the same day with luminance-following and coherent edge guards, a finest-level edge guard and stronger Color 100, and with edge-aware expansions, the coarsest level smoothed above Color 25 and the base image without the decode-time chroma clean-up). `3` (2026-10-16): the same multi-scale filter keeping more 8–30 px colour texture where those scales of the photo are quiet: from 1/8 of the resolution on, a scale's measured colour noise is taken as at most the finer scale's ÷ 1.7, and the thresholds of the 1/8 and 1/16 scales fall with their noise (2.5 + 2.75 · log2(noise / 0.012) multiples of it, between 2.5 and version 2's 8 / 7; `Tuning::for_version`). `4` (2026-10-17): the same filter as `3` with each scale built from the linear mean colour of the pixels it covers instead of the mean of their square-root chroma, so dark noisy colours keep their hue once the noise is removed (averaged square roots pulled a channel that is weak against its noise towards zero: lifted black fur turned blue; `Tuning::linear_means`); luminance and its noise measurement are unchanged, so Color 0 renders as `3`. `5` (2026-10-17): the same filter as `4`; at full resolution a pixel whose chroma is more than one unit of the colour noise from the median of its 3 × 3 neighbourhood takes that median to decide which side of a colour edge its edge-aware expansion follows (`Tuning::guide`, `Guide::Switch`; its own chroma otherwise, and its detail stays its own), so fewer isolated off-colour pixels remain along colour edges; Color 0 renders as `4`. `6` (2026-10-17): the same filter as `5`; the full-resolution detail is measured against the same edge-aware expansion of the coarser scale as the reconstruction (`Tuning::finest_detail_aware`), as the coarser scales already were; against the plain expansion a pixel next to a colour edge overshot past its own colour (halos, saturated rims on the dark side of an edge) or snapped to the other side's colour where its noisy chroma picked it (blotches along edges); colour transitions stay as wide as the photo has them (0.1–0.45 px wider than `5`); Color 0 renders as `5`. `7` (2026-10-18): the same filter as `6`; at full resolution a pixel whose chroma is more than two units of the colour noise from the median of its 3 × 3 neighbourhood while its square-root luminance is within one unit of the noise of theirs (an isolated off-colour pixel, not a coloured point brighter or darker than its surroundings) takes the median chroma as its detail (`Tuning::speck_swap`), so fewer isolated colour specks remain; Color 0 renders as `6`. `8` (2026-10-20): the same filter as `7`, judging the pixel's luminance after the luminance noise reduction instead of before it (`Tuning::speck_luma_after_nr`): a pixel brighter or darker than its neighbours only by noise that the luminance noise reduction takes back is an isolated off-colour pixel, a point it keeps standing out keeps its colour; with Luminance 0 and at Color 0 it renders as `7`. `9` (2026-10-20): the same filter as `8`; each pixel's filtered chroma is kept within the range, per component, of the plain reconstruction of the coarser scale at the pixel and its 8 neighbours (and of its own edge-aware reconstruction), widened by 1.5 units of the colour noise (`Tuning::range_clamp`): a pixel whose noisy chroma the detail kept along luminance and colour edges no longer stands out of its neighbourhood as a colour speck; the clamp weakens with the filter below Color 25 and above Detail 50, as the speck swap does, and fades out for chroma 4–8 units of the noise beyond the range, so a coloured point that far keeps its colour; Color 0 renders as `8`. `10` (2026-10-24): the same filter as `9`; the range leaves out the pixel's own edge-aware reconstruction (only the plain reconstruction at the pixel and its 8 neighbours) and is widened by 1.25 units of the colour noise (`Tuning::range_plain`, `RANGE_CLAMP_PLAIN`): where the coarser scale still holds some colour noise (mostly at Color 25), a pixel whose reconstruction or kept detail took its own noisy colour no longer stands out of its neighbourhood as a colour speck; Color 0 renders as `9`. `11` (2026-10-25): version `10`'s filter with its pyramid built, measured and rebuilt on the GPU from the renderer's input texture (`Tuning::gpu_pyramid`, `crates/gpu/src/shaders/color_noise_pyramid.wgsl`) for previews and exports alike, so a preview and its export take the same path; the CPU pyramid was the largest CPU stage of an export. Its pixels differ from `10`'s by the input's 16-bit float copy and the GPU's summation order (a mean of about 1 of 65535 per channel on the test frames), not by the filter; photos beyond the GPU's texture size limit (rendered in windows) keep the CPU pyramid. Without luminance noise reduction at Color 0 it renders as `10`. `2` to `10` recipes render exactly as before; all ten share the base image. `1`: the earlier cross-bilateral filter in the renderer. Without the key a recipe keeps what it rendered with before: `1` when it sets `colorNoiseReduction`, the newest (`11`) when a RAW recipe leaves it to the default (never-edited photos, headless exports without a recipe). The editor writes `11` into new edits, keeps a saved recipe's filter (also `2` to `10`) when loading it, and copies the key with the noise reduction group. Layers keep their colour amount: with version 2 to 11 a layer below the photo's amount blends towards the unfiltered colour, a layer above it gets the photo's filter, and a layer on a photo with Color 0 uses the cross-bilateral filter. With `2` to `11` the base image is developed without the decode-time chroma clean-up (preference `rawPreprocessingColorNr`; the multi-scale filter measures and removes the colour noise itself), with `1` as before (`BaseImageOptions::for_color_noise`); decoded-image cache keys and preview proxies record which base they hold, and the editor develops the open photo again when its filter changes. With `2` to `11` the luminance noise reduction also follows the photo's luminance noise by brightness (measured with the colour pyramid, also at Color 0) and, below Luminance 50, leaves a more even share of grain (2026-10-14); `1` recipes render their luminance exactly as before.

`adjustments.toneVersion` (2026-10-16, `crates/engine/src/image_processing.rs` `TONE_VERSION`, shader `cr_shadows_reach`, the `HL_V2_*` and `HL_V3_*` constants of `apply_highlights_adjustment` and `hl_v3_shift`): which response the tone sliders have under the RAW look. `3` (2026-10-25): as `2`, and lowering Highlights adapts to the image key (`image_key.rs`: the decode's median, 90th and 10th percentile of luminance): in dark frames (night streets, candles, lamps) it treats the frame as up to 2 EV brighter and compresses harder, so −100 reaches as far as Camera Raw's on broad bright areas there and darkens the upper midtones more; the shift is zero on frames of daylight or mid-tone key (those render as with `2`), faded in towards −100 (amount^0.5), none without a measured median (previews made before it), and faded out on nearly black frames as the 90th percentile falls from 2 EV over the black point to it (none at or below it, e.g. a moon on a black sky). `2`: Shadows above +50 lifts the quarter-tones further (display −8 … −1.5 EV, faded in quadratically from +50, so +50 and below render exactly as with `1`; at +100 it reaches the better of Capture One's and Camera Raw's Shadows +100 there), and lowering Highlights is refitted: it works in units of the look's exposure (the same display levels on every camera), −50 is about 0.4 of −100's change (Highlights −50 near Capture One's and Camera Raw's −50, −100 at least Camera Raw's reach), less of the upper midtones, more bright local detail; raising Highlights is unchanged. `1`: the earlier response. Without the key a recipe renders with `1` (old edits keep their look; the CLI and headless exports follow the recipe). The editor writes `3` into new edits and into loaded recipes without the key when nothing in them renders differently (no Shadows above +50 and no lowered Highlights on the photo or a layer); otherwise it keeps the recipe's version. The key is photo-wide (layers' Shadows and Highlights follow it), copied with the tone group and with Shadows in a tool copy, and reset with the Basic tool on the photo.

`adjustments.clarityVersion` (2026-10-24, `crates/engine/src/image_processing.rs` `CLARITY_VERSION`, shader `clarity_base` / `apply_band_contrast_log`): which response Clarity has, on the photo and its layers. `2`: a pixel's medium-scale band is its log2 luminance against a base taken from the large blur's mean log luminance (carried in the blurs' alpha, `blur.wgsl`) at the pixel and on two rings of eight points around it, plus the small blur's at the pixel, each weighted by how close it is to the pixel's own level (Gaussian over 0.2 EV), so a narrow bright edge pulls the base of its darker surroundings up less (smaller dark halos); amounts ×1.3 when raising and ×0.32 when lowering keep the texture gain of version 1 (12 calibration photos; 6 held-out photos: v2/v1 log gain 0.96 / 1.00 / 1.02 at −50 / +50 / +100). Missing (`1`): the band against the plain large blur. The editor writes `2` into new edits and into saved recipes without Clarity on the photo or a layer and states `1` in saved recipes that use Clarity without the key (so copied Clarity keeps its response); Presence's reset sets the current one; copied with Clarity (and the Clarity/Dehaze group).

`adjustments.curves.version` (and a layer's `curves.version`; 2026-10-21, `crates/engine/src/point_curve.rs` `LONG_CURVE_VERSION`, `WIDE_CURVE_VERSION`, shader `wide_curve_input`): how the point curves (`luma` = the RGB curve, `red`, `green`, `blue`) render. `3`: in the wide working space, as Camera Raw's do — the colour in ProPhoto primaries (Bradford D65 → D50) encoded with the sRGB curve, each channel through the RGB and its own curve, and back; nothing is clipped to sRGB or carried past the curves (the ProPhoto cube holds the whole working gamut). Only when a curve changes something: neutral curves skip the conversion and render as without the key. Measured against Camera Raw on two photos: 0.06 levels for a red channel curve (9.6 on display values), 0.66 for the RGB curve on saturated colours (1.46). `2`: on display values clipped to sRGB, with the part beyond sRGB carried at the curve's luminance ratio; curves of the photo with more than 16 points render whole (layers: their first 16). Missing (`1`): on display values, the first 16 points. The editor writes `3` into new edits and Lightroom imports write it; an edit of curves that already change something keeps their version (at least `2`), so moving a point of an older curve does not shift its colours; reset curves start at `3`. Curves of different versions compare equal where they render alike. Part of the curves, so it travels with them through copy, paste, presets and sync.

`adjustments.curves.luminance` (and a layer's; 2026-10-21, `crates/engine/src/point_curve.rs` `luminance_points`, shader `apply_luminance_curve`): the Luminance curve, points like the other channels (0–255, at most 16 render). After the RGB and channel curves, the colour's luminance (Rec. 709 Y of linear sRGB) goes through the curve on its sRGB encoding (the other channels' axis, so grey moves as under the RGB curve) and the linear colour is scaled by the ratio, at most 4× with the rest of the change added as grey (so a lifted black end lifts black, which scaling cannot): chromaticity, and with it saturation and hue, stays wherever the ratio is below 4. Missing or neutral: nothing (the shader skips it). Independent of `curves.version`. Capture One's `GradationCurveY` imports into it.

`adjustments.cameraCaVersion` (2026-10-17, `crates/engine/src/embedded_lens.rs` `CA_VERSION`): which cameras' own lateral CA data the camera lens mode (`lensCorrectionMode` `camera`) reads when the parameters are filled in from the RAW (saving, pasting, `apply_default`). `1`: also Panasonic's (RW2 IFD0 tag 0x011b, `embedded_lens::panasonic_chromatic`), which brings camera mode to Panasonic bodies that store CA data without distortion data (TZ81). Missing: Fujifilm's and Sony's only, as before, so a recipe saved again keeps its parameters. The rendering itself reads only `lensDistortionParams`. The editor writes `1` into new RAW edits and when the camera's correction is applied; headless exports of never-edited RAWs with camera data get it through `embedded_lens::apply_default`. Copied with the lens correction group.

`adjustments.diffractionCorrection` / `adjustments.diffractionVersion` (`crates/engine/src/diffraction.rs` `VERSION`): sharpening by the f-number and the pixel pitch, RAW only. The pitch comes from the file's FocalPlaneXResolution, else from the body's crop factor in the bundled Lensfun database. `diffractionVersion` `2` (2026-10-18, written when the correction is switched on, copied with it): the whole database. Missing (`1`): without the camera entries the 2026-10-18 database update added (`lens_correction::CAMERAS_ADDED_2026_10_18`: EOS R8 Mark II, PowerShot A710 IS, Z5IIC, OM System PEN, Lumix DC-L10, DC-TZ300/ZS300), so saved recipes render as with the earlier database; on those bodies they get no correction, as before. A later database update that adds a body or changes a crop factor needs a new version first (`lens_correction` test `the_camera_crop_factors_diffraction_reads_are_those_its_versions_know` fails until then). Offline photos keep both values in their source facts (`diffraction_sigma_v1` when it differs).

The vignetting and CA data read as before. `2`: also Nikon Z data framed as the camera's JPEG and Camera Raw frame them (`embedded_lens::nikon_curve`): an output radius u samples the sensor at u p(u) / (1 + V), V the framing scale NikonNEFInfo DistortionInfo stores at offset 0x40, with that zoom as the framing itself (`exact_zoom: true`). `3`: also Canon's distortion from CTMD record 14 (EOS R5 Mark II, R6 Mark III; `adjustments.lensProfileFor` (2026-10-18, `src-tauri/src/file_management/edits.rs` `LENS_PROFILE_FOR`): what the recipe's `lensDistortionParams` were resolved for — the lens mode and lens (chosen or detected; for the camera's own data its `cameraCaVersion` and, when present, `cameraGeometryVersion`) and the parameters themselves, as a string, or `"unresolved"` when no lookup was possible yet (no database or EXIF). A save keeps the parameters only while this matches (compared as JSON, numbers to within a few ulps, since a recipe read back from its sidecar or session can carry a parameter one ulp off); a new lens choice, a cleared or changed parameter set or `"unresolved"` is looked up again, so a Lensfun database update (renamed, re-measured or newly covered lens) reaches a saved edit only through a new lens choice or Auto lens correction. Missing (recipes saved before it): the parameters saved with the recipe count as resolved for its saved lens choice; the editor adds the key when it loads such a recipe. `adjustments.lutPath` / `adjustments.lutIntensity` (2026-10-24, `crates/engine/src/lut.rs`): the LUT and its amount, 0–200 (default 100; values above 200 render as 200). Auto Mask version (2026-10-18, `crates/engine/src/mask_generation.rs` `BrushLine`, `AutoMaskModel`): a brush stroke with `autoMask: true` may carry `autoMaskVersion`. Absent (every stroke before 2026-10-18, and strokes imported from Lightroom presets) is version 1: each dab keeps colours by their CIE Lab distance to the colour under its centre (fitted to Camera Raw), and such strokes render byte-identically to before. `2` is the edge-aware mask the editor writes for new strokes: per dab, the colours under it split into clusters, the one nearest the centre's colour is the subject, the others are backgrounds unless they are the subject's soft-edge mix, and a pixel keeps the subject's share of its linear-light mix with the nearest background; the stroke's coverage is then multiplied by the tip-weighted mean of its dabs' shares. `3` (2026-10-18, new strokes; `stroke_models_v3`) models the stroke's dabs together: each dab's subject is its cluster nearest the medoid of the subjects the dabs within three radii along the stroke pick by their centre's colour (a centre on a gap or highlight no longer turns the subject round); the dabs within six radii vote on which side of the stroke their backgrounds lie, and where that side is trusted a background cluster lying behind the centre counts as the subject's own and pixels behind the centre are kept whatever their colour (dark gaps in fur, shaded leaves). Strokes with `2` keep version 2, byte-identically. Versions 2 and 3 need the photo like version 1 does. ## Applied style

Optional `appliedStyle` (2026-10-26; `crates/engine/src/applied_style.rs`, `src/utils/appliedStyle.ts`): the style last applied from the styles list, `{"id": "…", "amount": 0…100, "changes": [{"path": ["exposure"], "from": 0, "to": 1}, …]}`. `changes` are the settings the style sets (also those it leaves as they were), at the deepest level of nested settings (`["hsl", "reds", "hue"]`, also inside a group the recipe did not have yet); lists and `curves` (points with their `version`) count as one setting. `from` is the value before the style, `to` the value it set, `full` (written by the editor once the Amount moved) its value at full strength; a missing `from`/`to` means the recipe did not have the setting. Applying another style or clicking the applied one again takes it back: each setting returns to `from` where the recipe still holds `to` exactly (numbers by value, missing = `null`); a setting the user changed after the style keeps the user's value and is the user's from then on (the Amount no longer moves it); other settings stay; a group the style added that ends up empty goes too. A style's groups of settings join the photo's own (a style that sets one HSL slider leaves the others as they were); other values replace the photo's. ## Relight

`relightLights` holds up to four non-generative projected lights. Each has an
`id`, `enabled`, `type` (`sun` or `spot`), sRGB hex `color`, `intensity` (0–100),
`x`/`y` (pattern center, −100…200 percent of the developed frame), `size` (5–200), `rotation`
(−180…180 degrees), `elevation` (5–90 degrees), `scale` (5–300), `softness`,
`diffusion`, `shadows` (all 0–100), `pattern` (`none`, `blinds`, `window`,
`strip`, `foliage`, `grid`, `palm`, `branches`, `checkerboard`, `dots`,
`horizontal`, `diagonal`, `weave`, `noise`, `crosshatch`) and `invert`.
Optional `sourceX`/`sourceY` (−100…200 percent) position the light independently
of the pattern; optional `patternRotation` (−180…180 degrees) rotates only the
pattern. Legacy recipes fall back to `x`/`y` for spot position and `rotation`
for pattern rotation, preserving their rendered output. Missing lights are identity.
`sectionVisibility.relight=false` bypasses all lighting without losing settings.
`relightOriginalLight` (0–100, default 100) scales the existing illumination
when at least one light has nonzero intensity. Up to analysis version 4 it
does not reconstruct albedo or remove the original light direction; version 5
(below) removes the original light's shading and skin shine on the subject.

Optional `relightDepth` contains `{data, geometry}`: a 16-bit grayscale PNG data
URL at inference resolution, and the geometry parameters at analysis time
(engine `relight::geometry`). Analysis uses the displayed GPU input frame, after lens/perspective correction,
orientation, flips, straightening and crop. Geometry records non-neutral crop
and straightening too; older maps remain valid only in their original neutral
frame. A geometry mismatch disables depth until the user analyzes again.
`relightDepthAmount` (0–100, default 60) controls normal strength; zero uses
projected lighting. Surface gradients are computed once using an edge-aware local slope fit on 16-bit
depth. A local curvature heuristic reduces unreliable normals near short
silhouette transitions, without changing height or exact linear planes.
The result is packed in a GPU texture and reused for light edits. Depth is specific to
the photograph and excluded from copy/paste and presets; light settings are
copyable. Analysis version 2 additionally stores `faces`: up to eight arrays of
468 `[x, y, z, confidence]` points (x/y normalized to the displayed frame; z is
camera-facing relief in short-side image units). They refine normals and local
height without rerunning inference on light edits. `version: 2` opts into the
refined light response; legacy maps remain compatible. Each light may store
`distance` (10–300, default 60), the spot source's image-relative distance.
Facial geometry remains photo-specific and is excluded from copy/paste.
No model inference or network request is needed to reopen or export
a recipe containing a depth map. The feature does not synthesize photo pixels
and does not add an AI patch.

Analysis version 3 keeps the same depth and facial geometry and defaults
`relightSkinReflections` (0–100) to 25; older analyses default to zero.
An explicit value overrides either default. This global, copyable setting adds
view-dependent dielectric reflections only within confident facial coverage,
using cached normals, a fixed skin-like roughness and the light's colour.
It does not recover skin/material parameters or remove existing highlights.
Zero, missing faces, disabled depth and stale geometry suppress the reflection.

Analysis version 4 additionally stores `camera` with normalized `fx, fy, cx, cy`,
`inverseMin`, `inverseMax` and `reference` (currently 1). A PNG code `v` decodes
as inverse distance `inverseMin + (inverseMax-inverseMin)*v/65535`. Distance
is relative, normalized by the analysis median, not metres. Version 4 requires
valid finite camera metadata; unknown newer versions are not decoded as old
height maps. The cache key includes the camera. Gradients, perspective positions,
face relief, view direction, gobo projection, spot falloff and local shadows all
use this camera. Facial relief scales with the face's local scene distance.
Surface amount zero flattens this geometry onto its reference plane, retaining
the same light transport. Scene normals are regularized without smoothing across
large depth jumps; only confident facial geometry casts local shadows.

Analysis version 5 (new analyses since 2026-10-15) keeps version 4's fields
and smooths the scene slopes over a wide, depth-aware window when they are
loaded (monocular depth blotches backgrounds and skies). For a subject of at
least 5 % of the frame (BiRefNet matte) it adds `subject`, an RGBA PNG data
URL (8 bits per channel; 16-bit ones from earlier builds read the same) at
up to 1024 px per side and twice that wide: the left half holds
the subject normal's x and y (renderer frame: x right, y down, z towards the
camera), the matte and the normal's weight; the right half the share of the
photo that is the original light's skin shine and how far a new light reaches
the background (the inverse square of its distance relative to the
subject's). The subject, as a card at its median depth, casts its shadow on
that background (only the matte occludes). People
(faces, or skin in the whole-photo parse for profiles) take DAViD's normals,
objects the smoothed scene normals. `sourceLight` (nine numbers: ambient,
light, direction x/y/z, four zeros) is the photo's own lighting fitted on the
people's skin or the object's dominant material, scaled so the subject's lit
side has shading 1; a new light is divided by this shading, so it lights the
material (`I·L/S`) and Original light 0 % leaves only the new light, and the
skin shine is reduced with the original light. `subjectDepth` is the subject's
median inverse depth. Outside the matte the scene is lit evenly (no normal
response). Recipes of versions 2–4 render as before (byte-identical exports).

Optional light field `rangeVersion` (2026-10-31, new lights `2`; absent = 1)
names the ranges the light's values mean (engine `relight::intensity_gain`,
shader `range2`). Range 1: Intensity 0–100 % is a linear gain 0–3; Softness
only blurs pattern and cast-shadow edges, Diffusion lifts pattern shadows and
widens the terminator of objects (people keep a fixed one), Face reflections
are a bare dielectric lobe. Range 2: gain `4 · (intensity/100)^1.5`; on
surfaces Softness wraps the light around them (`wrap = 1.2 · softness`,
response `(N·L + wrap)/(1 + wrap)`, at least 0.15 on people), Diffusion mixes
the response towards 0.5 (light reaching surfaces turned away), and the
light's face reflections are 12 times stronger. Ranges were measured on four
portraits and three scenes (notes: benchmark-results/rl-relight-ux-2026-10-31).
Lights of range 1 render as before; the editor's *Use the current ranges*
moves one to range 2 at the same gain.

Analyses since 2026-10-31 may store `relightDepth.subjectCenter` (`[x, y]`,
normalized): the centre of the subject matte's opaque part, where the
editor's lighting presets go when no face was found. The renderer does not
read it.

Since 2026-10-13: absent light fields render with a new light's values
(intensity 25, rotation 135, shadows 100, colour `#fff1db`; engine
`relight::DEFAULT_*`, parity-tested against `createRelightLight`). Earlier
recipes with fields missing therefore render with these values. The editor
writes `sourceX`/`sourceY`/`patternRotation`/`distance` explicitly when it loads
a recipe (same rendering). Optional light fields: `number` (stable display
number), `temperature` (Kelvin the colour came from; `color` stays
authoritative), `maskId` (limit the light to that mask layer; a hidden or empty
layer switches the light off, a deleted one no longer limits it), and
`pattern: "custom"` with `customPattern: {id, data, name}` — a 512×512 grayscale
PNG data URL made from the chosen image's central square (white transmits
light), copied with the light. A custom light without its bitmap is
unpatterned. `relightDepth.cacheKey` names an analysis: previews send its
bitmap and landmarks once and then only the name, as with AI patches; files
without a key are named by a hash of the bitmap when loaded.

### Two-sided linear gradient bands

A `linear` mask may contain optional `parameters.band: { width, feather }`.
Both values are nonnegative distances in the mask's image frame, before preview
scaling. `width` is the full-width strip of 100% coverage centered on the existing
start–end line; `feather` is the linear falloff outward from each edge to zero.
A zero feather gives a hard edge. The existing `range`/`rangeEnd` values remain
stored for switching back to the ordinary gradient, and are ignored while a band
is present. Without `band`, the existing gradient calculation is unchanged.
Frame transforms scale both band distances along the line's normal, matching the
existing gradient ranges. Invert, opacity and mask composition apply as usual.

## Generated patch provenance

`adjustments.aiPatches[].patchData.model` optionally records the model that produced the stored fill pixels: `moebius`, `mi-gan`, or `external`. It records the model actually used, including fallback; earlier patches without the field remain valid and are listed as model not recorded. It does not alter rendering. Visible model-generated patches with nonempty `patchData.color` carry the existing export Digital Source Type marking; clone, heal, liquify, retouch and patches marked `generated: false` do not. The shared predicates live in `rawtonic_metadata::provenance` and feed the catalog’s AI-edit index as well as export. A patch without pixels is indexed as an unfinished fill, not a generated area.
