# npm install scripts: allowScripts pins, not --ignore-scripts

Measured 2026-11-01 (task DS2, Linux PC): `npm ci` in `services/relay` under Node 26 (26.13.0, npm 11.20.0) installed all 72 packages and exited 0 with the lockfile's esbuild 0.28.2 both on a warm cache and on a cold one (`--cache` into a fresh directory), with scripts run in order and both postinstalls exiting 0 — and the same on Node 24.22.2. esbuild 0.28.2 (latest on npm, engines `node >=18`) has no separate Node 26 release to bump to, and the binary import resolves without the postinstall at all. So the defect's "esbuild's postinstall fails under Node 26" was not reproducible on this host; do not change a gate or drop a script on that account without a log of the failing install (Node and npm version, machine).

- **How Node 24+/npm 11+ treat install scripts.** npm moved away from running every package's scripts implicitly; a script runs only for a package listed in `allowScripts` (`"<name>@<version>": true` in `package.json`, pinning the exact version — a version bump needs a new entry, which is the point). The root `package.json` already carries such entries (`esbuild@0.28.2`, `@swc/core@1.16.1`). `npm install-scripts approve <pkg>` writes an entry.
- **Keep the gate plain `npm ci`.** With `allowScripts` pinned, plain `npm ci` on 11.19/11.20 runs exactly the allowed scripts, and on a new npm that enforces the list strictly it still does. `--ignore-scripts` would also skip real postinstalls we rely on (the relay's tests run in Miniflare's `workerd`, whose own postinstall writes `node_modules/workerd/bin`; `npx wrangler dev`/`deploy` needs it on a fresh install). Use `--ignore-scripts` only in a scratch directory where no binary is needed.
- **A postinstall that wrote nothing is not a failure first.** A global `allow-scripts` list in a user `~/.npmrc` (or a tool adding one) can skip scripts silently. If a binary such as `node_modules/.bin/esbuild` is missing after `npm ci`, re-run the install with `--foreground-scripts` and read the `run <pkg> postinstall { code: … }` lines before touching the script.
- Host pitfall (not a repo defect): this Linux PC's shell carries `NODE_ENV=production`, and npm then omits `devDependencies`; a direct `npm ci` in `services/relay` (all its tools are dev dependencies) installed nothing and printed `up to date`. Run such measurement installs with `env -u NODE_ENV`; `scripts/check.sh` is unaffected (its fresh installs are not the truncated `NODE_ENV=production` form npm treats as a production install).
