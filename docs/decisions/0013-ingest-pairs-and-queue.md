# ADR 0013 — RAW+JPEG pairs and resumable ingests
Status: accepted (2026-10-20). Side-by-side use test against Lightroom Classic and Capture One open (G59, G66).

**Context.** Cameras set to RAW+JPEG (or RAW+HEIF) write two files of one name per exposure. Lightroom Classic imports such a pair as one photograph by default: the RAW is the photograph, the JPEG is kept with it as a sidecar (copied, moved and removed with it) and is not a photograph of its own; a preference imports the JPEGs as separate photographs instead. Capture One imports both files as images of their own; keeping them apart from each other is left to filters or stacks afterwards. (Both from the editors' documentation and earlier notes; not yet observed side by side on our test cards.) Until now Rawtonic imported both as separate photographs, and a card sidecar named after the stem alone (`NAME.xmp`) was matched only as `.xmp` or `.XMP`, and only with the photograph's exact letter case.

**Decision.** Rawtonic takes Lightroom's way, since for the photographer a pair is one exposure: one entry in the grid, one rating, label and edit, and no JPEG left behind when the RAW is moved or deleted. The ingest (`rawtonic_ingest::batch::pair_sources`) pairs a RAW and a JPEG or HEIF of the same name (letter case aside) in the same folder when both were chosen. The RAW is imported as before (name, date folder, card sidecar, backup copy); the JPEG is copied verified and without replacing anything beside the RAW's copy under the RAW's new name with its own extension (and beside the backup copy), and recorded as the RAW's companion (`assets.raw_jpeg_pair`, the file name beside the photograph, with its size and content fingerprint) in the same transaction as the photograph. A name free for both files is chosen, so the pair always keeps one name. Only exactly one RAW and one such image of a name pair up: a name shared by more files (RAW and DNG, JPEG and HEIF) or files of one name in different folders (cameras number each folder on their own; two card slots) stay photographs of their own. The import dialog offers "Import JPEGs next to RAW files as separate photos" when the chosen files contain pairs (both editors allow separate photographs; for Capture One it is the only way). "Add where they are" pairs the same way, recording the JPEG with the RAW without writing anything beside the files.

A companion is part of its photograph everywhere: the library never registers it again (folder index, Add, Synchronize Folder), folder listings leave it out, it moves and goes to the Trash with its RAW, and the RAW's `NAME.xmp` is the RAW's. Renaming a photograph keeps the companion's name (the record names the file, so it stays valid). Only the recorded file counts as the companion: a file of that name with another size or content (the RAW moved or relinked next to another JPEG) is a photograph of its own and is never hidden, moved or trashed with the RAW. A companion whose file is gone keeps its name reserved: importing that JPEG again puts it back, and no other copy takes the name. Duplicate detection covers companions: a JPEG whose content the library already holds as a photograph or a companion is skipped; when the RAW is already in the library, the JPEG is checked on its own and comes in as a photograph of its own if it is new, so nothing chosen is left out. A companion whose copy fails leaves the RAW imported alone with the reason reported.

Card sidecars (`capture::card_sidecar`) are matched ignoring ASCII letter case (`NAME.EXT.xmp` before `NAME.xmp`, any case of either part). Two files that differ only in case for the same form (possible on a case-sensitive volume) are reported and neither is copied, since which holds the photographer's metadata cannot be told.

**Resumable ingests (G66).** Every copy ingest is a job in the library's database (`tasks`, kind `ingest`, with one `ingest_items` row per photograph: source, companion, number for `{seq}`, state; schema 10). Before a photograph is copied, its planned copy and its companion's are recorded (`copying`); after the library recorded it, the item is `done`. A quit or crash leaves the job running in the database; opening the library again finishes it in the app (`session_ingest_resume`, reported as an import is): copies a cut-off run published but did not record are recorded (with the companion), the rest is copied with the names and numbers it would have had. Meanwhile the folder index, Add and Synchronize Folder leave such planned copies to the job, so a pair is never registered as two photographs. Each source is kept with its size and modification time: a file at its place that is not it (another card with files of the same names, the camera's numbering started again) is never resumed in its place; a RAW whose JPEG is gone or changed comes in alone. Planned copies and a destination folder inside the library are kept relative to it, so a closed session moved elsewhere resumes in its new place. The album an import goes into is kept with the job: a resumed run puts every photograph of the job into it, those of the cut-off run included. Photographs whose card or drive is not connected wait (the job is `interrupted`; the app says so and offers to forget them), a copy the library could not record (busy, disk full) is recorded by the next run, and a job the user cancelled is not resumed. We found no documented way in Lightroom Classic or Capture One to resume an interrupted import; that is to be checked in the side-by-side use test. Copy rules are unchanged: sources are only read, copies are verified and never replace a file.

**Consequences.** A library opened by this version is migrated to schema 10, which older Rawtonic versions refuse to open (as with every schema change). The companion cannot be opened, rated or exported on its own (as in Lightroom); a user who wants that imports with separate JPEGs. Copy (duplicate) of a photograph does not copy its companion.
