# ADR 0016 — Moving photos between volumes

Status: accepted (2026-10-23). Side-by-side use test against Lightroom Classic and Capture One open (G40).

**Context.** `rawtonic-fileops` journals rename, move and trash with undo and redo, but every step is a rename, so a move to a folder on another drive was refused. A rename cannot cross volumes; the move has to be a copy and a removal of the original, and both halves must be safe for RAW originals: a crash at any point may never lose both copies, never leave a half file under the photo's final name, and never delete an original outright. Lightroom Classic and Capture One move photos between drives by copying and removing the source; neither documents a byte-for-byte check or an undo of such a move. RAWmakase 0.4.2 copies, compares byte for byte, sends the original to the Trash, keeps an original that changed meanwhile or whose drive has no Trash, journals every step, names the drive, the bytes to copy and the free space before it starts, and refuses FAT, exFAT and network drives; it has no undo. (Editors' behaviour from their documentation and release notes, not observed side by side here.)

**Decision.** One move tool; it picks per file: a rename on the same volume, otherwise a *copy move* (`Target::OtherVolume`), carried out in three journaled phases:

1. **Copy (invisible).** Each file is copied into a staging folder the operation makes next to its target (`.rawtonic-moving-<operation id>/`, created exclusively, so nothing else writes there) under its step number (a short name, whatever the length of the photo's), recorded in the journal before the file is made. The copy keeps the permission bits and the modification time, is synced (`fsync`) with its folder, and is then read back and compared byte for byte with the source. Linux drops the copy's cached pages first (`POSIX_FADV_DONTNEED`), so the comparison reads what reached the drive; macOS reads with `F_NOCACHE`, which does not evict pages already cached. The source's size and modification time are recorded with the verified copy. Only then is the step marked copied.
2. **Publish (visible).** Every step in order: renames as before; copies are renamed from the staging folder to their final name with an exclusive rename (`renameat2(RENAME_NOREPLACE)` / `renamex_np(RENAME_EXCL)`), never a check-then-rename. The sources are still in place. A failure, a cancel or a crash in phases 1–2 rolls back: renames go back, published copies go back into the staging folder (only when they still equal their source), and the staging folder is removed, deleting only the names the journal recorded inside it.
3. **Finish (originals to the Trash).** The operation is marked finishing. First every copy is checked to be at its destination unchanged (its size and modification time; after a crash its bytes, compared again, since a drive may have been swapped before the next start). If one is gone or changed, nothing more goes to the Trash and the whole operation is rolled back: originals already trashed come back from the Trash, copies that still equal their originals are taken back, so a photo's RAW, sidecars and virtual copies never end up in two places. Otherwise each source goes to the system Trash (the app's `SystemTrash`, never an unlink) while its size and modification time are unchanged; a source that changed since it was verified, or that its drive cannot put in a Trash, is kept (both copies exist, the records follow the copy) and the operation's note says so. A crash here is finished, or rolled back by the same check, at the next start: both copies exist until a source goes to the Trash, and a trashed source is recorded to be put back.

Refused clearly before anything is copied: folders (moving a folder between drives is not supported yet), links and anything but a regular file; a target volume that cannot rename exclusively (probed in the staging folder: exFAT and FAT on macOS answer `ENOTSUP`; on Linux the exfat and vfat drivers support `RENAME_NOREPLACE`, measured on a loop-mounted exFAT image, so they are allowed); network file systems (NFS, SMB/CIFS, AFP, WebDAV, and macOS volumes without `MNT_LOCAL`), whose sync and read-back do not prove what reached the disk; and too little free space (the bytes to copy on each target volume plus a 64 MiB reserve). The Library asks first, naming the target drive, the bytes to copy and the free space there, and that the originals go to the Trash of their drive.

**Undo and redo.** Undo of a copy move is a copy move back the same way: the current bytes at the target (edits made since included) are copied next to the original place, verified, published there, and the copies at the target go to the Trash; the originals sent to the Trash by the move stay there. Where the move kept an original (changed, or no Trash), undo only trashes the target copy, and only when both are still byte-identical; otherwise it refuses. A crash during an undo's copy or publish phase rolls the undo back (the operation stays done); one during its finish phase finishes it. Redo validates the plan again and copies again. Catalog and session records follow through the same `renames()` pairs as same-volume moves, so asset ids, edits and albums are kept and relative session paths are re-keyed by the existing sync.

**Progress and Stop.** The copy phase reports bytes copied to a callback and checks a cancel flag between blocks, during verification and before publishing; Stop rolls back like a failure. The app clears the flag when an operation takes the journal's lock, so Stop never reaches the next operation.

**Not taken / open.** Folders between volumes; macOS exFAT/FAT targets (no exclusive rename; a reserved placeholder name would leave an empty file under the final name after a crash); network drives; extended attributes (Finder tags) and ACLs are not copied; Windows has no exclusive-rename probe yet (the existing fallback is check-then-rename, so cross-volume moves are refused there). The macOS paths (`renamex_np`, `F_NOCACHE`, `statfs` flags) compile in CI only on Linux; they need a run on a Mac.

**Consequences.** Journal payloads may contain `otherVolume` steps and the new states `finishing` and `undoFinishing`; an older Rawtonic reading such a row fails to parse it rather than misreading it.
