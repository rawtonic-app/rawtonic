# ADR 0016 — Moving photos and folders between volumes

Status: accepted (2026-10-23). Side-by-side use test against Lightroom Classic and Capture One open (G40).

**Context.** `rawtonic-fileops` journals rename, move and trash with undo and redo, but every step is a rename, so a move to a folder on another drive was refused. A rename cannot cross volumes; the move has to be a copy and a removal of the original, and both halves must be safe for RAW originals: a crash at any point may never lose both copies, never leave a half file under the photo's final name, and never delete an original outright. Lightroom Classic and Capture One move photos between drives by copying and removing the source; neither documents a byte-for-byte check or an undo of such a move. RAWmakase 0.4.2 copies, compares byte for byte, sends the original to the Trash, keeps an original that changed meanwhile or whose drive has no Trash, journals every step, names the drive, the bytes to copy and the free space before it starts, and refuses FAT, exFAT and network drives; it has no undo. RAWmakase 0.4.3 adds whole folders (the entire folder is copied and verified, files outside the catalog included, before the catalog follows; originals to the Trash where the source drive has one). (Editors' behaviour from their documentation and release notes, not observed side by side here.)

**Decision.** One move tool; it picks per file: a rename on the same volume, otherwise a *copy move* (`Target::OtherVolume`), carried out in three journaled phases:

1. **Copy (invisible).** Each file is copied into a staging folder the operation makes next to its target (`.rawtonic-moving-<operation id>/`, created exclusively, so nothing else writes there) under its step number (a short name, whatever the length of the photo's), recorded in the journal before the file is made. The journal records each first source's Unix permission bits when its volume supplies them (FAT-family modes are synthesized and not recorded). On a POSIX destination, the copy uses those recorded bits without execute or special bits, further restricted by the live source's mode when it is on a POSIX volume. An unrecorded mode (including old journals and FAT-origin moves) uses 0644 masked by the current umask, also restricted by any live POSIX source mode; undo and redo keep the first recorded mode as a ceiling. A failure to set permissions on the staged POSIX file aborts before publication and rolls back. FAT-family and NTFS/FUSE-block modes are treated as synthesized. No copied photo is made executable, even for a POSIX-to-POSIX move. The copy keeps the modification time, is synced (`fsync`) with its folder, and is then read back and compared byte for byte with the source. Linux drops the copy's cached pages first (`POSIX_FADV_DONTNEED`), so the comparison reads what reached the drive; macOS reads with `F_NOCACHE`, which does not evict pages already cached. The source's size and modification time are recorded with the verified copy. Only then is the step marked copied.
2. **Publish (visible).** Every step in order: renames as before; copies are renamed from the staging folder to their final name with an exclusive rename (`renameat2(RENAME_NOREPLACE)` / `renamex_np(RENAME_EXCL)`), never a check-then-rename. The sources are still in place. A failure, a cancel or a crash in phases 1–2 rolls back: renames go back, published copies go back into the staging folder (only when they still equal their source), and the staging folder is removed, deleting only the names the journal recorded inside it.
3. **Finish (originals to the Trash).** The copies are in place and verified: from here they are the photos and nothing is rolled back. Each source goes to the system Trash (the app's `SystemTrash`, never an unlink), checked just before it goes: its size and modification time must be unchanged since its copy was verified, and its copy must still be at the destination with the size and modification time it had then. A source that fails either check, or whose drive has no Trash, is kept: both copies exist, the records follow the copy, and the operation's note says so. A crash here is finished at the next start without trashing anything more: the sources still there are kept and the note says so (both copies exist; what happened to a drive meanwhile is an offline drive like any other, not a reason to move records back). Earlier review rounds tried rolling a move back from this phase when a copy had changed at recovery; that needed originals put back from the Trash and still left windows where a photo's files split, so this phase keeps instead of rolling back.

Refused clearly before anything is copied: links and anything but a regular file or a folder (also anywhere inside a moved folder); a target volume that cannot rename exclusively (probed in the staging folder: exFAT on macOS answers `ENOTSUP`; FAT32 on macOS 27, whose FAT driver runs in FSKit, supports `RENAME_EXCL`, and on Linux the exfat and vfat drivers support `RENAME_NOREPLACE`, measured on disk images, so they are allowed); network file systems (NFS, SMB/CIFS, AFP, WebDAV, and macOS volumes without `MNT_LOCAL`), whose sync and read-back do not prove what reached the disk; and too little free space (the bytes to copy on each target volume plus a 64 MiB reserve). The Library asks first, naming the target drive, the bytes to copy and the free space there, and that the originals go to the Trash of their drive.

**Undo and redo.** Undo of a copy move is a copy move back the same way: the current bytes at the target (edits made since included) are copied next to the original place, verified, published there, and the copies at the target go to the Trash; the originals sent to the Trash by the move stay there. Where the move kept an original (changed, or no Trash), undo only trashes the target copy, and only when both are still byte-identical; otherwise it refuses. A crash during an undo's copy or publish phase rolls the undo back (the operation stays done); one during its finish phase finishes it, keeping the copies not yet trashed. Redo validates the plan again and copies again; a copy an undo kept at the destination (its original's trashing was interrupted, or failed) is taken as the copy when it still holds the original's bytes, and refused as an existing file otherwise. Catalog and session records follow through the same `renames()` pairs as same-volume moves, so asset ids, edits and albums are kept and relative session paths are re-keyed by the existing sync.

**Folders (2026-10-24).** A folder moves as one copy-move step (`CopyState::folder`), never as one step per file: everything below it is listed without following links (a link or special file anywhere in it refuses the folder), copied into the staging folder under the step's number with its folders and every file, each file synced, read back and compared as above, the folders synced deepest first, and then the source is listed again — a file added, removed or changed meanwhile fails the copy and rolls back. The journal records the listing with both stamps per file (`CopyState::tree`). Publishing is one exclusive rename of the whole staged folder to its final name, so the folder appears complete or not at all. In phase 3 the original folder goes to the Trash as one item, only when its listing still equals the verified one exactly (nothing added, removed or changed: an added file was never copied) and every verified copy is still in the published folder unchanged (files added there since do not matter); otherwise it is kept and the note says so. Undo copies the folder back as it is at the target then (edits and files added since included) and trashes the target folder the same way; a kept original is only taken back when both folders hold the same files with the same bytes. Rolling back a published folder and redo over a kept copy use the same whole-folder comparison. Permissions: files as above, each entry's first mode recorded (`CopyState::modes`) as its ceiling; folders get their source's bits bounded by the recorded mode and the umask, always keeping the owner's access (so a read-only folder's copy can still be managed and trashed). A folder moving to another drive is the only step of its operation (the app never mixes them), so what keeps a published folder copy (below) concerns that one step. A published folder is never taken back: a failure, Stop or crash after it appeared (in practice only the instant before phase 3) rolls the operation back with both the verified copy and the untouched original in place, and the note and error say so — taking it back again kept producing windows in which something writing into the visible folder could lose bytes (review rounds 3–4), the same lesson as phase 3. An undo or redo stopped after it published a folder records it as kept, so that a retry takes it over, and its error names the folder that stays. Staging cleanup removes from an unpublished staged folder only files at paths the moved folder has (recorded with its copy, or at either end now), then the folders left empty, and only directly inside a staging folder the journal names — anything else stays, with the staged folder, and the note says so. Another drive mounted inside the folder refuses it (its checks would not apply). The app moves a folder with "Move Folder…" in the Folders menu (a folder picker; the session's own folders and library roots stay fixed, a folder holding a session or catalog is refused, since its database may be open, and a folder moves only within its session or outside any — photos leaving a session are kept there as missing, which a folder move does not do; catalogs keep originals anywhere, so their folders move freely); on another drive it asks first, naming the folder, its photos, files and bytes, the drive and its free space, and the Trash the original goes to. The catalog and previews follow the folder pair like a folder rename. On macOS FAT/exFAT/SMB drives, AppleDouble companions `._name` of a listed file are not listed (the system keeps them with their file; not run on a Mac yet).

**Extended attributes (2026-10-24).** A copy keeps the extended attributes a program may set — on Linux the user namespace (`user.*`; `security.*`, `system.*` with the ACLs and `trusted.*` belong to the system and are not copied); on macOS every attribute except those the system keeps itself (`com.apple.provenance`, which it puts on every file a program writes, `com.apple.rootless` and `com.apple.system.*`), so Finder tags and comments, resource forks, download origins and quarantine travel. They are read from the open source before its bytes, written to the staged copy (files, and folders with what is in them), read back from the copy after the sync and compared, and the source's must still be the same at the end of the copy, like its size and time. Before anything is copied, when a source (or anything in a moved folder) has such attributes, each staging folder is probed by setting one on a probe file: a drive that cannot keep them (FAT and exFAT on Linux) refuses the move there and then, so nothing is copied and the source stays where it is, and the message names the drive, the file and its attributes; the Library's question shows that refusal instead of asking. In phase 3 a source goes to the Trash only while its attributes (in a folder: every entry's) still equal its copy's; otherwise it is kept and the note says so. The comparisons that decide whether two copies are the same (taking back a published copy, undo over a kept original, redo over a kept copy) include the attributes. Windows alternate data streams do not arise: moves between drives are refused on Windows.

**Publishing in place (2026-10-24).** A volume whose exclusive rename is answered as unsupported (`ENOTSUP`/`EINVAL`/`ENOSYS`: exFAT on macOS) but which refuses a second exclusive creation of a name gets its files published in place (`Publish::InPlace`, decided per staging folder and journaled before any final name is created): each file is created exclusively (`O_CREAT|O_EXCL`) under its final name, its creation journaled before a byte is written (`CopyState::created`), then copied, synced, read back and compared there, so the name is never taken from anyone else. Such a file is visible while it is copied; until the move finishes it is removed again — on failure, Stop, rollback of an undo or crash recovery — only when this direction created it and it holds the start of its source's bytes (or all of them) and no extended attribute the source lacks, while the source is a file of its own, so nothing is lost that the source does not hold (a Finder comment another program gave the copy meanwhile keeps it). A copy that fails in the running process is also taken back when it holds exactly the bytes this direction wrote (their length and a hash kept for that process) and no attribute but those it was to be given, while its source is still a file of its own, so an original changed while it was copied leaves nothing under the final name; one whose source vanished stays. When journaling a creation fails, the file just created is taken back the same way. Its attributes are set create-only (`XATTR_CREATE`), so one another program gave the visible copy meanwhile is never replaced; the copy then fails and is kept. A crash between the creation and its journal entry can leave an empty file under the final name; recovery does not remove it (it might be someone else's) and the note names it. Folders are refused on such volumes (their photos can move). Measured on Linux with the mode forced (tmpfs, ext4, exFAT, vfat): a crash at every journal point of a move (26 points), undo (27) and redo (26) leaves only starts of copies before recovery and nothing after (3 unjournaled empty files named per phase); Stop, a name taken meanwhile and a copy written by someone else are covered. On macOS 27.0.1 (Apple silicon, exFAT disk image attached without root, tests run serially) the probe chooses publishing in place; the in-place suite, crash injection at every journal point of move, undo and redo included, passes on the real volume, and 8 threads creating the same 400 names exclusively never had two winners, a name differing only in case counting as taken (`exclusive_creation_has_one_winner_per_name`). The tests of staged copies and of folders skip on such a volume (`publishes_in_place`).

**Progress and Stop.** The copy phase reports bytes copied to a callback and checks a cancel flag between blocks, during verification and between publishing steps; Stop rolls back like a failure. In the app each run gets a number, sent with its progress; Stop names it and is ignored for any other run, so a Stop button left from one operation never stops the next.

**macOS (run 2026-10-23, macOS 27 on Apple silicon, disk images attached without root).** The whole copy-move suite passes from the APFS startup disk to an APFS image and to a FAT32 image (`RAWTONIC_TEST_OTHER_VOLUME`), crash injection included, and the system Trash (`NSFileManager trashItemAtURL`) takes an item on such a drive into that drive's `.Trashes/<uid>` and puts it back. exFAT's macOS driver answers `renamex_np(RENAME_EXCL)`, `RENAME_SWAP` and `link` with `ENOTSUP`, so no name can be published by renaming without check-then-rename; its files are published in place instead (above). FAT32's `RENAME_EXCL` held under contention: 8 processes renaming onto the same 400 names never had two winners, and a name differing only in case counts as taken. Two FAT properties the move lives with: modification times are kept in steps of up to 2 s, so the "unchanged since verified" checks on a FAT drive miss a same-size change within that step; and macOS keeps a file's extended attributes (here every file the tests wrote carried `com.apple.provenance`) in an AppleDouble companion `._name` beside it, which the system renames and removes together with its file.

**Permission-fix validation (2026-10-23).** Local fileops tests pass using the explicit copy-move seam, including permission ceilings, restrictive umask, legacy journals, repeated undo/redo and crash recovery. The real-FAT rerun remains unverified: a concurrent run on a FAT32 image stalled after four tests, its processes stayed in kernel exit after interruption, and forced detach did not finish. The new FAT-origin regression has not been verified on a real FAT volume. The earlier macOS results above describe the pre-fix suite.

**Not taken / open.** Links inside a moved folder (refused, not copied as links); drag and drop of a folder onto another in the Folders panel (only the menu and its picker); macOS exFAT targets (above); network drives; ACLs are not copied (nor Linux `security.*`/`trusted.*` attributes); macOS attribute handling (which names the system lets a program set; AppleDouble on FAT/exFAT) not run on a Mac yet; a separate move back from FAT cannot recover an earlier operation's original mode (it uses the default; undo/redo of the recorded operation restores the mode); Windows has no exclusive-rename probe yet (the existing fallback is check-then-rename, so cross-volume moves are refused there). The macOS read-back with `F_NOCACHE` may still be served pages the copy left cached; that is not measured.

**Consequences.** Journal payloads may contain `otherVolume` steps and the new states `finishing` and `undoFinishing`; an older Rawtonic reading such a row fails to parse it rather than misreading it.
