# ADR 0016 — Moving photos between volumes

Status: accepted (2026-10-23). Side-by-side use test against Lightroom Classic and Capture One open (G40).

**Context.** `rawtonic-fileops` journals rename, move and trash with undo and redo, but every step is a rename, so a move to a folder on another drive was refused. A rename cannot cross volumes; the move has to be a copy and a removal of the original, and both halves must be safe for RAW originals: a crash at any point may never lose both copies, never leave a half file under the photo's final name, and never delete an original outright. Lightroom Classic and Capture One move photos between drives by copying and removing the source; neither documents a byte-for-byte check or an undo of such a move. RAWmakase 0.4.2 copies, compares byte for byte, sends the original to the Trash, keeps an original that changed meanwhile or whose drive has no Trash, journals every step, names the drive, the bytes to copy and the free space before it starts, and refuses FAT, exFAT and network drives; it has no undo. (Editors' behaviour from their documentation and release notes, not observed side by side here.)

**Decision.** One move tool; it picks per file: a rename on the same volume, otherwise a *copy move* (`Target::OtherVolume`), carried out in three journaled phases:

1. **Copy (invisible).** Each file is copied into a staging folder the operation makes next to its target (`.rawtonic-moving-<operation id>/`, created exclusively, so nothing else writes there) under its step number (a short name, whatever the length of the photo's), recorded in the journal before the file is made. The copy keeps the permission bits and the modification time, is synced (`fsync`) with its folder, and is then read back and compared byte for byte with the source. Linux drops the copy's cached pages first (`POSIX_FADV_DONTNEED`), so the comparison reads what reached the drive; macOS reads with `F_NOCACHE`, which does not evict pages already cached. The source's size and modification time are recorded with the verified copy. Only then is the step marked copied.
2. **Publish (visible).** Every step in order: renames as before; copies are renamed from the staging folder to their final name with an exclusive rename (`renameat2(RENAME_NOREPLACE)` / `renamex_np(RENAME_EXCL)`), never a check-then-rename. The sources are still in place. A failure, a cancel or a crash in phases 1–2 rolls back: renames go back, published copies go back into the staging folder (only when they still equal their source), and the staging folder is removed, deleting only the names the journal recorded inside it.
3. **Finish (originals to the Trash).** The copies are in place and verified: from here they are the photos and nothing is rolled back. Each source goes to the system Trash (the app's `SystemTrash`, never an unlink), checked just before it goes: its size and modification time must be unchanged since its copy was verified, and its copy must still be at the destination with the size and modification time it had then. A source that fails either check, or whose drive has no Trash, is kept: both copies exist, the records follow the copy, and the operation's note says so. A crash here is finished at the next start without trashing anything more: the sources still there are kept and the note says so (both copies exist; what happened to a drive meanwhile is an offline drive like any other, not a reason to move records back). Earlier review rounds tried rolling a move back from this phase when a copy had changed at recovery; that needed originals put back from the Trash and still left windows where a photo's files split, so this phase keeps instead of rolling back.

Refused clearly before anything is copied: folders (moving a folder between drives is not supported yet), links and anything but a regular file; a target volume that cannot rename exclusively (probed in the staging folder: exFAT on macOS answers `ENOTSUP`; FAT32 on macOS 27, whose FAT driver runs in FSKit, supports `RENAME_EXCL`, and on Linux the exfat and vfat drivers support `RENAME_NOREPLACE`, measured on disk images, so they are allowed); network file systems (NFS, SMB/CIFS, AFP, WebDAV, and macOS volumes without `MNT_LOCAL`), whose sync and read-back do not prove what reached the disk; and too little free space (the bytes to copy on each target volume plus a 64 MiB reserve). The Library asks first, naming the target drive, the bytes to copy and the free space there, and that the originals go to the Trash of their drive.

**Undo and redo.** Undo of a copy move is a copy move back the same way: the current bytes at the target (edits made since included) are copied next to the original place, verified, published there, and the copies at the target go to the Trash; the originals sent to the Trash by the move stay there. Where the move kept an original (changed, or no Trash), undo only trashes the target copy, and only when both are still byte-identical; otherwise it refuses. A crash during an undo's copy or publish phase rolls the undo back (the operation stays done); one during its finish phase finishes it, keeping the copies not yet trashed. Redo validates the plan again and copies again; a copy an undo kept at the destination (its original's trashing was interrupted, or failed) is taken as the copy when it still holds the original's bytes, and refused as an existing file otherwise. Catalog and session records follow through the same `renames()` pairs as same-volume moves, so asset ids, edits and albums are kept and relative session paths are re-keyed by the existing sync.

**Progress and Stop.** The copy phase reports bytes copied to a callback and checks a cancel flag between blocks, during verification and between publishing steps; Stop rolls back like a failure. In the app each run gets a number, sent with its progress; Stop names it and is ignored for any other run, so a Stop button left from one operation never stops the next.

**macOS (run 2026-10-23, macOS 27 on Apple silicon, disk images attached without root).** The whole copy-move suite passes from the APFS startup disk to an APFS image and to a FAT32 image (`RAWTONIC_TEST_OTHER_VOLUME`), crash injection included, and the system Trash (`NSFileManager trashItemAtURL`) takes an item on such a drive into that drive's `.Trashes/<uid>` and puts it back. exFAT stays refused: its macOS driver answers `renamex_np(RENAME_EXCL)`, `RENAME_SWAP` and `link` with `ENOTSUP`, so there is no way to publish a name without check-then-rename (a reserved placeholder would leave an empty file under the final name after a crash, and replacing it is still a check-then-rename). FAT32's `RENAME_EXCL` held under contention: 8 processes renaming onto the same 400 names never had two winners, and a name differing only in case counts as taken. Two FAT properties the move lives with: modification times are kept in steps of up to 2 s, so the "unchanged since verified" checks on a FAT drive miss a same-size change within that step; and macOS keeps a file's extended attributes (here every file the tests wrote carried `com.apple.provenance`) in an AppleDouble companion `._name` beside it, which the system renames and removes together with its file.

**Not taken / open.** Folders between volumes; macOS exFAT targets (above); network drives; extended attributes (Finder tags) and ACLs are not copied; a photo moved to a FAT drive and back takes that drive's permission bits (`rwx------`), not its own; Windows has no exclusive-rename probe yet (the existing fallback is check-then-rename, so cross-volume moves are refused there). The macOS read-back with `F_NOCACHE` may still be served pages the copy left cached; that is not measured.

**Consequences.** Journal payloads may contain `otherVolume` steps and the new states `finishing` and `undoFinishing`; an older Rawtonic reading such a row fails to parse it rather than misreading it.
