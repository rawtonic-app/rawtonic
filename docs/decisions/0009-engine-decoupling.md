# ADR 0009 — Engine decoupling strategy
Status: accepted, 2026-10-08. Refines the extraction boundaries of ADR 0001.

## Starting point (measured 2026-10-08, branch `claude/editing-tools` at 633e231)
`rawtonic-app` holds 80 modules and 79,500 lines. 29 modules (14,900 lines) are transitively free of Tauri, `AppState` and `lib.rs` helpers, but all of them sit in the Tauri crate, so nothing outside the app (CLI, tests, benches) can use them, every engine edit recompiles the whole adapter, and nothing stops new code from reaching back into `AppState`. Three couplings carry most of the knot:

1. `image_processing` (5,200 lines) is the hub: it mixes the adjustment model (`GlobalAdjustments`, `MaskAdjustments`, JSON → GPU uniforms), geometry, CPU detail stages, scopes, auto analysis, a Tauri command and the GPU context with the native display. It imports 13 modules and is imported by almost every other one.
2. `lib.rs` works as a service locator: `get_original_image`, `get_cached_full_warped_image`, `apply_all_transformations`, `generate_transformed_preview`, `load_settings` and others are called from `mask_generation`, `spot_removal`, `inpainting`, `ai_commands`, `export_processing`, `lut_processing` and `tagging`.
3. GPU work is reached through `tauri::State<AppState>` (`gpu_processing`: context, processor and texture caches live in `AppState`; the display surface needs the window).

The RAW decode path is the exception: `raw_processing` needs only `image_processing::apply_orientation` and the profiling/allocator helpers from outside its own closure.

## Target layering
Dependencies point downwards only; no crate below the app depends on `tauri` or on `rawtonic-app`.

| Layer | Crate | Contents |
|---|---|---|
| 0 | `rawtonic-runtime` | Process helpers shared by every layer: opt-in stage timing (`profiling` feature) and explicit allocator release. |
| 1 | `rawtonic-rawdecode` | RAW bytes → oriented linear camera RGB plus capture metadata: rawler front end, demosaic (CPU, GPU X-Trans), DNG opcodes, highlight reconstruction, hot pixels, maker-note parsing, camera colour (matrices, DNG colour, per-unit calibration), baseline exposure tables, noise level. |
| 2 | `rawtonic-engine` | Develop model and CPU stages: adjustment structs and their JSON translation, geometry, detail stages, scopes, auto analysis, camera defaults and looks, colour tools, mask definitions and rasterisation, lens correction maths. |
| 3 | `rawtonic-gpu` | `GpuProcessor`, shader variants and render requests against an explicit device/queue and caller-owned caches; the app keeps the window surface. |
| 4 | `rawtonic-export` | Full-resolution render, encoders, metadata embedding; a headless export entry point that does not start Tauri. |
| 5 | `lens`, `ai`, `tether` | Lensfun database and lens profiles, ONNX models and connectors, gphoto2 — extracted when they have a non-Tauri consumer. |
| app | `rawtonic-app` | Tauri commands, `AppState`, caches, file management, `session_bridge`, windowing, QA channel. |

`rawtonic-catalog`, `-metadata`, `-naming` and `-ingest` stay independent of all engine crates.

## Method
- **Move, do not rewrite.** Files move with `git mv` and unchanged bodies; only visibility (`pub(crate)` → `pub`), crate paths and feature names change. A module that mixes core and glue is split: the core moves, Tauri commands and `AppState` access stay in an app module of the same name.
- **Shims keep call sites stable.** The app re-exports a moved module under its old name (`pub use rawtonic_rawdecode::raw_processing;`), so `crate::raw_processing::…` keeps resolving and a move does not touch dozens of callers in the same commit. Shims are removed once callers import the crate directly.
- **Break the knots by passing data, not state.** Functions that take `tauri::State<AppState>` or call `lib.rs` helpers get their inputs as parameters (image, adjustments, device/queue, cache handle); the command wrapper in the app fetches them from `AppState`. No new global registries are introduced to dodge a parameter.
- **Features forward.** `rawtonic-app/performance-profiling` enables `performance-profiling` in the lower crates, so profiling builds log the same stages. Helpers that only the app's GPU tests need sit behind a crate's `test-support` feature, enabled through the app's dev-dependencies, never in release builds.
- **Tests follow the code.** Unit tests move with their module; ignored evaluation tools that need app services (the image loader with its EXIF cache) move to an app test module (`engine_tools.rs`) instead of making the crate reach back up.
- **Enforced direction.** `scripts/check_layering.sh` runs in CI and fails when a library crate below the app reaches `tauri` through its normal dependencies.
- **One phase per commit series, no behaviour change mixed in.** A refactor commit must not change pixels. Fixes found while moving code are separate commits.

## Verification gate for every phase
- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked` (moved unit tests now run in their crate), the GPU equivalence tests (`cargo test -p rawtonic-app --lib -- --ignored`), `npm run typecheck`.
- Byte-identical full-resolution 16-bit TIFF exports of the in-scope public corpus (raw.pixls.us files, one per in-scope model, `refs/raw-pixls`, 285 files) from release binaries of the commit before and after the phase. Any differing file blocks the phase until explained.
- Release timing of the same exports is recorded; cross-crate calls are not inlined without LTO, so a slowdown above noise means adding `#[inline]` at the hot boundary, not accepting it.

## Phases
1. **Runtime + rawdecode.** Create layers 0 and 1; `apply_orientation` moves to rawdecode; the CLI gains a decode benchmark that exercises the crate without Tauri.
2. **Engine core.** Split `image_processing`: the adjustment model, geometry, CPU stages and scopes move; `GpuContext`, the display and the Tauri command stay. Move the pure look/colour modules (`color_grading`, `region_curve`, `calibration`, `film_simulation`, `adobe_profile_curves`, `icc_profile`, `lens_blur`, `guided_perspective` core) and the default-adjustment modules (`baseline_exposure`, `auto_adjust`, `diffraction`, `camera_profile` core) with it; `MaskDefinition` moves out of `mask_generation`; the rasteriser follows in phase 3 (it still reads the AI mask parameter types and the warped-image cache).
3. **GPU.** `GpuProcessor` and render requests move to `rawtonic-gpu`; `AppState` keeps the context, caches and window surface; `lib.rs` helpers used by masks/spots/AI take explicit inputs.
4. **Export.** Full-resolution export without Tauri; the CLI gets `export`. Unlike phases 1–3 this is not move-only; measured blockers (2026-10-08): `export_processing` calls four state-bound `lib.rs` helpers (`apply_all_transformations`, `generate_transformed_preview`, `hydrate_adjustments`, `load_settings`) and the app-side mask/warp lookups; source loading goes through `image_loader` (decoded-image cache in `AppState`, the EXIF cache write, Apple RAW); metadata goes through `exif_processing`, which reads and writes editor sidecars via `session_bridge` and `file_management::read_file_mapped`; the result is registered in the session with `session_bridge::write_new_output`. Order:
   1. Move the pure export stages (resize/pad/border/canvas geometry, watermark, encoders, ICC tagging, `xmp_embed`, `tiff_exif`, `webp_container`) into `rawtonic-export`, with tests.
   2. Give the pipeline one input type — source pixels, the hydrated recipe, capture metadata, settings — built by the app from `AppState`/sidecars and by the CLI from a file and an optional recipe JSON; the app's `lib.rs` helpers become functions of that input plus the engine/GPU crates.
   3. Move the orchestration (`process_image_for_export_pipeline` and the encode/save path); output registration in the session stays a callback the app supplies (`session_bridge`), the CLI writes with the no-clobber helpers only.
   4. Gate: the app's headless export and `rawtonic export` must produce byte-identical files on the corpus, neutral and edited, and both must match the commit before.
5. **Lens, AI, tether** when a consumer outside the app needs them.

Not in scope: the ProPhoto/DCP working space, a redesigned engine API or render graph, frontend restructuring. Those remain open gaps; this ADR only makes the existing engine usable and testable without the desktop adapter.
