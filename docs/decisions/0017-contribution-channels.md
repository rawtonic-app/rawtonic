# ADR 0017 — Contribution channels and the relay

Status: accepted (2026-10-24). Design only; the relay (`services/relay/`) and the app's shared core follow in their own pull requests, the four channel UIs after that. Nothing described here sends anything until its channel ships and is listed in `PRIVACY.md`.

**Context.** Most photographers will not open a GitHub account or write a bug report, yet crash data, camera behaviour and RAW samples of poorly supported cameras are the most valuable inputs Rawtonic can get. The user decided on 2026-10-24 to offer four ways to contribute without an account: (1) "Report a problem" in the app, (2) a crash report offered on the next start, (3) camera help — the guided tether camera test's result and the donation of a RAW sample, and (4) anonymous usage statistics. Each is opt-in, each send shows exactly what will be sent first, statistics are off by default. Until now `PRIVACY.md` promised "no accounts, analytics, telemetry or crash reporting"; the update check (PR #263) is the only automatic network access.

**Threat and privacy model.** What must not leak: who the user is (account names, home folder, host name, e-mail), where and what they photograph (folder and file names, GPS, faces in photos, people's names in text), which camera body they own (serial numbers), and anything that links two submissions to one person. Adversaries: (a) a passive reader of the stored reports (the maintainers, or anyone who gains access to the private repository or bucket) — limited by sending as little as possible, scrubbing before the preview and deleting on a schedule; (b) spammers and abusers of a public endpoint — limited by rate limits, size caps, strict schemas and an optional proof of work; (c) a stolen relay secret — the GitHub token can only touch one private repository, the bucket holds only donated samples and screenshots. Not in scope: hiding the user's IP address from Cloudflare, which runs the relay (it sees every request's IP like any web host; the relay itself stores no IP, see Abuse protection), and from GitHub, which never sees the user (the relay files issues, not the app).

**Decision.**

*One relay, no account.* The app talks only to one small HTTPS service, a Cloudflare Worker in `services/relay/` (deployed by the user: `docs/RELAY.md`). It validates every submission against the schemas below, rate-limits, files reports and crashes and camera tests as issues in a **private** GitHub repository through a bot token held only by the relay (Worker secret), keeps screenshots and RAW samples in a **private** R2 bucket (RAW samples are not filed as issues; the maintainers list them from the database and bucket), and keeps statistics only as aggregated counters in D1. No third-party SDK, tracker or CAPTCHA, in the app or the relay.

*The app never sends on its own.* The relay URL is built into the app (`RAWTONIC_RELAY_URL` at build time); a build without it has no contribution channels. The client makes one attempt per send (no retries, no background queue, no redirects followed), with a 10 s connect timeout and a 30 s total timeout (uploads: 30 s plus 1 s per MiB). Every send goes through one "Review what will be sent" dialog that shows the exact request body (pretty-printed JSON, the screenshot as an image, sizes); the bytes shown are the bytes sent — the dialog hands back the body it displayed together with its SHA-256, and the client refuses a body whose digest does not match or that the scrubber would still change. Statistics (below) are the one channel that sends without a click each time, and only after the user switched them on: there the preview is the opt-in screen plus "Show what is sent" at any time, since a confirmation every week would turn the opt-in into a nag (the user's decision asks for a preview before every send; this reading is open for the user to confirm).

*Consent at the moment of use, not at first run.* There is no first-run question. Each channel asks when it is relevant: a "Report a problem…" menu item; a crash prompt on the next start, asked once per crash (Send / Don't send; either answer removes the pending crash file); a "Send result" button at the end of the camera test; "Donate a RAW sample…" in the camera test and the photo's context menu, with two required checkboxes (the licence below; "this photo may show people, places or the camera's serial number, and I am allowed to give it"). Statistics are switched on only in Preferences → Privacy (default off), where the payload of the next send can be viewed at any time ("Show what is sent") and the last sent payload is kept for viewing.

*Scrubbing (app side, before the preview).* Applied to every text field the app fills (log lines, crash message and backtrace, system info) and to the user's own text: absolute paths become `<path>` with only the file extension kept (`/Users/anna/Pictures/Anna-wedding.CR3` → `<path>.CR3`), covering POSIX, `~/`, `C:\…`, `\\server\share\…` and `file://` URLs; the user's account name and the host name anywhere become `<user>` / `<host>`; values after serial-number keys (`SerialNumber`, `BodySerialNumber`, `serial`, `InternalSerialNumber`, `LensSerialNumber`, …) become `<serial>`; e-mail addresses become `<email>`; IPv4/IPv6 addresses become `<ip>`; GPS coordinate pairs become `<gps>`. The relay repeats a cheap check and refuses (422) a body that still contains a home-folder path (`/Users/<name>/`, `/home/<name>/`, `C:\Users\`). Photos are never scrubbed — a RAW sample is donated as is, which is why its consent names faces, GPS and serial explicitly.

*Payloads (schema 1; JSON, UTF-8; unknown fields are refused).* Common block `app`: `{version, os: "macos"|"windows"|"linux", osVersion (major.minor), arch}`; optional `gpu: {vendor, name}` (adapter name as the driver reports it, ≤ 100 chars).

| Endpoint | Body | Caps |
|---|---|---|
| `POST /report` | `{schema, app, gpu?, text, logTail?, photo?: {make, model, fileType}, screenshot?: {mime: image/png\|image/jpeg, data: base64}}` | text ≤ 10 000 chars, logTail ≤ 24 K characters (last 200 lines); an issue body above GitHub's limit (fences grow with backtick runs) is shortened, longest part first, keeping a log's end and a backtrace's start, with a note of what was left out, screenshot ≤ 2 MiB decoded, body ≤ 3 MiB |
| `POST /crash` | `{schema, app, gpu?, message, location, backtrace?, logTail?, crashedOn: YYYY-MM-DD}` | message ≤ 2 000, location ≤ 300, backtrace and logTail ≤ 24 K characters each (so the issue stays within GitHub's 65,536-character body limit), body ≤ 96 KiB |
| `POST /camera-test` | `{schema, app, camera: {make, model, firmware?}, report}` (`report` = the camera test's existing anonymous Markdown report) | report ≤ 16 KiB, body ≤ 32 KiB |
| `POST /raw-sample` | `{schema, app, camera: {make, model}, fileType, size, sha256, licence: "rawtonic-sample-1", personalDataAcknowledged: true, note?}` → `{id, ref, uploadUrl, expiresAt}`; then `PUT uploadUrl` with the file | file ≤ 100 MiB (Workers request limit), note ≤ 1 000, upload URL valid 1 h, used once |
| `POST /stats` | `{schema, week: "YYYY-Www", app, gpuVendor, cameras: [{make, model}], tools: {<key>: true}}` | ≤ 50 cameras, tool keys from a fixed list, body ≤ 8 KiB |
| `DELETE /report/:id` | — (the id is the capability) | — |

Strings are trimmed, control characters other than newline and tab are refused, make/model ≤ 64 chars, file type ≤ 10 chars (letters and digits). `make`/`model` are the camera library's names, never a serial or owner name.

*Report ids and deletion.* Every stored submission (report, crash, camera test, RAW sample) answers `{id, ref}`: 128 random bits as 26 base32 characters, shown to the user in the confirmation with "Copy" and a note that the id deletes the submission. The relay stores only its SHA-256, so the id itself appears nowhere at rest; the issue names a short reference (the first 8 hex digits of that hash) for support conversations. `DELETE /report/:id` deletes the issue (GitHub GraphQL `deleteIssue`, which also removes the edit history an edit would keep), the R2 objects and the index row; it answers 204, 404 for an unknown id, or 409 while a RAW sample is still uploading (an upload claims the record by compare-and-swap before writing; a removal deletes the issue and objects first and the record last, only if it is unchanged, so an interrupted or overtaken removal leaves the record for the next try). Every filing records its row before it writes to the bucket or GitHub and gives the id out only when all is recorded. A filing that fails is undone at once when its outcome is known. When GitHub got the request but no answer came back, the issue may exist without its number recorded; the relay does not hunt for it (earlier designs that searched for it kept leaving new half states): the record and objects are removed two hours later, the sender has an error and no id, and the issue, if it exists, is deleted by the age-based issue retention below like every other. RAW samples involve no GitHub write at all. The app keeps the ids of its own sends in a local list ("Sent reports" in Preferences → Privacy) so the user can delete without having copied the id. Statistics have no id and cannot be deleted one by one: they are only counters (below) and hold nothing about a person.

*Retention.* A scheduled run every 10 minutes, sized to the Workers Free plan's 50 subrequests and 50 D1 queries per run, does three independent steps, so a GitHub outage never holds up the rest: housekeeping; records and their objects by age from D1 (reports, crashes and camera tests 90 days after receipt, RAW samples two years after receipt, rows whose request stopped half-way after two hours); and issues by age read from the repository itself, oldest first, deleted 90 days after they were created — whether or not a record names them. RAW samples are kept two years (they serve decoder and colour work across releases). Closing an issue does not end retention early; the maintainers copy plain camera facts from camera tests (e.g. into `tetherCameras.json`) before then. Rate-limit rows live until their window ends (an hour, a day, or a week for statistics), upload tokens one hour and proof-of-work stamps 20 minutes. Statistics: weekly counters are kept two years; a week's counters below the k threshold are folded into `(other)` when the week is closed (two weeks after its end), so rare values are not kept at all.

*RAW sample licence ("rawtonic-sample-1").* The donor confirms they own the photo or may give it, and grants Rawtonic's maintainers a non-exclusive, free, revocable licence to keep the file privately and use it to develop and test Rawtonic (decoding, colour, lens and noise work), never to publish or redistribute it and never to train generative models; numbers measured from it (e.g. white levels, noise profiles) may enter Rawtonic. Revocation is the delete route above. The exact text ships in the app with the dialog and is quoted in `PRIVACY.md`.

*Statistics without a persistent ID.* The app counts locally, per ISO week, only: which camera makes/models were opened in Rawtonic (deduplicated), which tools from a fixed list were used at least once (yes/no, never counts, values or times), and sends at the first start of a later week one body for the previous week, if statistics were on for that week. There is no install id, no session id, no timestamp finer than the week, no locale, no screen size; app version, OS and its major.minor version, architecture and GPU vendor (Apple, AMD, Intel, NVIDIA, Qualcomm or other) are the only system values. Weeks the app was not used send nothing; the relay accepts a week only from its end until two weeks later, so the app drops unsent weeks older than that. The relay increments one counter per (week, dimension, value) in D1 — `os=macos`, `camera=SONY ILCE-7M3`, `tool=masks` — and never stores the body, so values from one send are not linked to each other afterwards. Reading needs the admin token (`GET /stats/summary?week=`) and shows only values counted at least **k = 10** times that week; the rest is reported as one `(other)` line. Abuse: two stats sends per IP hash per week (two installs behind one router), values outside the allowlists refused.

*Abuse protection.* Rate limits are counted per IP hash: `HMAC-SHA256(IP_HASH_KEY, window || ip)`, a secret key with the limit's window (the hour, the UTC day, or for statistics the ISO week) mixed in, so the hash of one address changes with every window and cannot be reversed without the key; only the hash and a counter are stored, until the window ends. Every request counts, also one refused afterwards as invalid. Limits per IP hash: report 5/hour and 20/day, crash 10/day, camera test 10/day, RAW sample 3/day, stats 2/week, delete 30/hour; plus global caps per day (400 issues, 200 RAW samples, 5 GiB uploaded) so a botnet cannot fill the repository or the bucket — beyond them the relay answers 429 and the app says "try again later". Requests must be `application/json` (uploads `application/octet-stream`) with an `X-Rawtonic-Client: <version>` header; the relay sends no CORS headers, so web pages cannot call it. Optional proof of work (off by default, `POW_BITS` in the Worker's variables): the client sends `X-Rawtonic-Pow: <unix-seconds>.<nonce>` such that `SHA-256("rawtonic-pow-1:" + seconds + ":" + sha256hex(body) + ":" + nonce)` starts with `POW_BITS` zero bits; stamps older than 10 minutes or seen before are refused. Proof of work instead of a CAPTCHA keeps third parties out; 20 bits cost a laptop well under a second.

*What lives where.* Cloudflare Worker (code: this repository; secrets: `GITHUB_TOKEN`, `IP_HASH_KEY`, `ADMIN_TOKEN` via `wrangler secret`, never in git); D1 database `rawtonic-relay` (index of submissions: id hash, kind, issue number and node id, R2 keys, received date; rate-limit counters; upload tokens; statistics counters); R2 bucket `rawtonic-contributions` (private, no public access: `screenshots/<hash>.<ext>`, `raw-samples/<hash>/<make>-<model>.<ext>` with `sample.json` beside it holding the announced camera, licence and note); GitHub: issues in the private repository named in `GITHUB_REPO` (labels `report`, `crash`, `camera-test`), filed by a bot account that is an admin of that repository only (needed for `deleteIssue`). Worker logs (observability) are off; error responses carry no request data.

**Not taken.** A third-party crash or analytics service (Sentry, Plausible, …): data would leave our control and add an SDK. Asking at first run: consent should be given when the user knows what it is for. A persistent install id for deduplicating statistics: it would make every send linkable. Uploading RAW samples straight to R2 with presigned URLs: needs S3 credentials and a signing library in the relay; the Worker streams the upload itself and verifies its SHA-256 (`R2Bucket.put` with `sha256`). Files above 100 MiB (some medium-format RAWs) need multipart uploads — open. GitHub issue attachments for screenshots: the API offers no upload; the issue links the bucket object instead.

**Consequences.** `PRIVACY.md` gets a section per channel when that channel ships (until then it says none exists); `AGENTS.md`'s privacy guardrail names this ADR. The relay is a public endpoint the maintainers operate: its secrets, retention runs and the private repository are their responsibility, and deployment is a user action (`docs/RELAY.md`). A change to any payload is a new `schema` number, accepted by the relay alongside the old one until no supported app sends it.
