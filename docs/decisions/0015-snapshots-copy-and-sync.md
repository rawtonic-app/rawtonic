# ADR 0015 — Snapshots, copy and sync of settings
Status: accepted (2026-10-20; copy and sync 2026-10-21). Side-by-side use test against Lightroom Classic and Capture One open (G26, G27).

**Context.** The Develop history (G26) names each step (PR #87) but keeps it only while a photograph is open; the catalog keeps every saved recipe as a version's history chain. There were no snapshots: a photographer could not keep "warm" and "mono" of one photograph under names and go back to either. Lightroom Classic has snapshots (a Snapshots panel; a new one is named with the date and time, can be made from any history step, renamed, deleted, updated with the current settings; clicking one applies it as a history step); Capture One has variants (separate versions of a photograph with thumbnails) and no snapshots. Rawtonic already has virtual copies (Lightroom's virtual copies, Capture One's variants), kept by the library since the offline work (G58). (Editors' behaviour from their documentation and earlier notes; not yet observed side by side here.)

**Decision: snapshots.** A snapshot is a name, an id, the time it was taken and the adjustments of one moment, of one version (a photograph's primary version or one virtual copy; a new copy starts without any). One tool, Lightroom's model with Capture One's thumbnails: the Snapshots tool beside History in every Develop tab lists them with a thumbnail developed from their adjustments as the Library develops thumbnails (`snapshot_thumbnail`: from the file, decoded for the snapshot's colour noise filter, never from the open photograph's decoded image, which holds the current edit's decode-time development; AI Denoise is left out as in Library thumbnails), + takes one of the current edit named with the date and time (the name is selected to type over), the camera on a history step takes one of that step named after it, the pencil renames, the arrows update one with the current edit, × deletes. Clicking one restores it as one history step named after it ("Snapshot Warm"), so Undo returns to the edit before; restoring changes nothing else.

The library keeps them in their own table (`snapshots`, schema 12; long strings stored once in `recipe_blobs` like the history's, referenced through `snapshot_blob_refs` so pruning keeps them), never in the recipe history: taking one is no edit, and twenty snapshots do not make every later history step twenty times larger. The editor state the library hands out carries them, so the `.rrdata` sidecar derived from it carries them too (`snapshots`, with each long string once under `snapshotStrings`: twenty snapshots of a photograph with three AI masks wrote 18.5 MB per save as plain copies, 1.8 MB like this). The library's are authoritative: a save carrying an older list changes nothing, and the sidecar is derived again with the library's. A library that adopts a sidecar (a photograph added, a database built again, a virtual copy's sidecar found) takes over its snapshots when the version has none; broken entries are left out with a log line rather than refusing the photograph's edit. A photograph in no library keeps them in its sidecar only. XMP sidecars do not carry them: Rawtonic never reads the recipe back from XMP, and their metadata is unchanged by snapshots (tested).

**Decision: copy, paste and sync settings (G27).** One picker for Copy (⇧⌘C) and Sync (⇧⌘S, the open photograph's settings onto the other selected ones): every setting by tool group, by section (Lightroom's Copy/Sync Settings dialog), a "Changed" choice of the groups the photograph changed plus its layers (Capture One's auto-selection of adjusted tools), and the local layers one by one (Capture One's clipboard). The choice is remembered; Option-click (Copy, Sync) uses it without the picker. The clipboard holds exactly what was chosen and Paste (⇧⌘V) applies all of it (no merge of defaults: what was chosen is what is pasted). Processing versions (the photo-wide responses values are rendered with: tone sliders, sharpening, noise reduction, Defringe, AI Denoise…) are an entry of their own, off by default, as Lightroom treats Process Version: unchosen, each photograph keeps its own and the pasted values render with them (a never-edited photograph: a new edit's), so no setting that was not chosen changes; chosen, the source's travel (a missing one as missing), which the picker says can change how the other settings of those photographs look. Previous (⌥⌘V, Lightroom's) applies the saved settings of the photograph open before, as last chosen. Edit all selected stays the automatic sync.

Rules: pasted or synced layers join each photograph's own: a layer of the same id (pasted before) is replaced, the others are added on top, its own layers stay (Edit all selected mirrors the primary's layers instead). AI selections never take the source's bitmap onto another photograph: they are pasted without it and marked pending, shown at the layer's component. Subject, Sky, depth range and People are detected on that photograph when it is opened; an Object selection (pointed at one photograph's object) says "Select again" until the user points at the object there. A virtual copy of the same photograph keeps the bitmap, since it shares the pixels. Until then exporting that photograph fails with a message naming the photograph and each layer and what to do (app and CLI), rather than rendering the layer with another photograph's mask or without one; detecting at export, and mapping an Object box through both photographs' geometry for automatic re-detection, are follow-ups (G27). Retouching (spots, face retouch), AI patches (generated pixels, with their IPTC marking on their own photograph), Relight's depth and lens blur belong to their photograph and are never copied. Lens Correction is copied as the lens choice (mode, lens, camera CA version, amounts), never as the source's lens data: each destination resolves it for its own camera, lens and focal length as its save does (an offline photograph's camera correction from the facts registered for it). On the open photograph the paste is one step at once with the lens marked unresolved, so an export or save before its data arrives resolves it there; the data then goes into the paste's step and the later steps that still have that choice (undone ones too), never over a later lens edit. Lightroom documents re-detecting AI masks on each photograph when syncing; not observed side by side here.

**Not taken / open.** Spot removal (heal, clone) cannot be synced yet (Lightroom syncs it, Capture One copies heal layers): spots need framing like drawn masks. Detection at export (and before thumbnails) of pending AI selections. Lightroom's "create virtual copy from snapshot" is not built (take the copy, restore the snapshot on it). The history itself is still the editor's in memory while a photograph is open (G26). The use test against Lightroom and Capture One is open.

**Consequences.** A library opened by this version is migrated to schema 12 (no snapshots yet), which older Rawtonic versions refuse to open. Measured (debug build with the dev profile's opt-level 1, Linux PC, `snapshot_timing`): a snapshot of a library photograph with three 300 KB mask bitmaps takes 58 ms (the editor's recipe save of that photograph 53 ms), the list of twenty 2.6 ms, the editor's save with twenty snapshots held 73 ms.

Sync measured (dev profile opt-level 1, Linux PC, `sync_timing`; the recipe writes the command waits for, not the thumbnails regenerated after): 100 photographs (hard links of one CR3 or RAF) take 0.44 s when their EXIF is in the library, 6.5 s the first time (each photograph's EXIF read, 65 ms); with NEF files 5.4 s every time (EXIF read again per write: a lead, not looked into).
