# ADR 0015 — Snapshots, copy and sync of settings
Status: accepted (2026-10-20). Side-by-side use test against Lightroom Classic and Capture One open (G26, G27).

**Context.** The Develop history (G26) names each step (PR #87) but keeps it only while a photograph is open; the catalog keeps every saved recipe as a version's history chain. There were no snapshots: a photographer could not keep "warm" and "mono" of one photograph under names and go back to either. Lightroom Classic has snapshots (a Snapshots panel; a new one is named with the date and time, can be made from any history step, renamed, deleted, updated with the current settings; clicking one applies it as a history step); Capture One has variants (separate versions of a photograph with thumbnails) and no snapshots. Rawtonic already has virtual copies (Lightroom's virtual copies, Capture One's variants), kept by the library since the offline work (G58). (Editors' behaviour from their documentation and earlier notes; not yet observed side by side here.)

**Decision: snapshots.** A snapshot is a name, an id, the time it was taken and the adjustments of one moment, of one version (a photograph's primary version or one virtual copy; a new copy starts without any). One tool, Lightroom's model with Capture One's thumbnails: the Snapshots tool beside History in every Develop tab lists them with a thumbnail developed from their adjustments (`snapshot_thumbnail`, from the open photograph's decoded image), + takes one of the current edit named with the date and time (the name is selected to type over), the camera on a history step takes one of that step named after it, double-click renames, the arrows update one with the current edit, × deletes. Clicking one restores it as one history step named after it ("Snapshot Warm"), so Undo returns to the edit before; restoring changes nothing else.

The library keeps them in their own table (`snapshots`, schema 12; long strings stored once in `recipe_blobs` like the history's, referenced through `snapshot_blob_refs` so pruning keeps them), never in the recipe history: taking one is no edit, and twenty snapshots do not make every later history step twenty times larger. The editor state the library hands out carries them, so the `.rrdata` sidecar derived from it carries them too (`snapshots`, with each long string once under `snapshotStrings`: twenty snapshots of a photograph with three AI masks wrote 18.5 MB per save as plain copies, 1.8 MB like this). The library's are authoritative: a save carrying an older list changes nothing, and the sidecar is derived again with the library's. A library that adopts a sidecar (a photograph added, a database built again, a virtual copy's sidecar found) takes over its snapshots when the version has none; broken entries are left out with a log line rather than refusing the photograph's edit. A photograph in no library keeps them in its sidecar only. XMP sidecars do not carry them: Rawtonic never reads the recipe back from XMP, and their metadata is unchanged by snapshots (tested).

**Not taken / open.** Lightroom's "create virtual copy from snapshot" is not built (take the copy, restore the snapshot on it). The history itself is still the editor's in memory while a photograph is open (G26). The use test against Lightroom and Capture One is open.

**Consequences.** A library opened by this version is migrated to schema 12 (no snapshots yet), which older Rawtonic versions refuse to open. Measured (debug build with the dev profile's opt-level 1, Linux PC, `snapshot_timing`): a snapshot of a library photograph with three 300 KB mask bitmaps takes 58 ms (the editor's recipe save of that photograph 53 ms), the list of twenty 2.6 ms, the editor's save with twenty snapshots held 73 ms.
