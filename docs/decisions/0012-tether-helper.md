# ADR 0012 — Tethering in a helper process
Status: accepted (2026-10-18). Hardware qualification per body pending (G46/G48).

**Context.** The inherited tethering (RapidRAW) called libgphoto2 inside the app, behind a build feature that was never shipped: a crash in a camera driver or a USB transfer that hangs would take the app (and any unsaved state) with it, the capture was saved outside the catalog and the file on the camera was deleted afterwards. libgphoto2 is LGPL-2.1-or-later.

**Decision.** The camera library runs only in a separate program, `rawtonic-tether` (crate `crates/tether`), which the app starts on demand and talks to over its stdin/stdout (length-prefixed JSON frames and camera JPEG frames for live view; a protocol number is checked at start). One helper thread owns the camera and polls its events between requests, so photos fired on the body arrive like the ones the app asks for. Downloads are published crash-safely into the session's `.tether/incoming/<slot>/` (temporary file, fsync, size check against the camera's report, no-clobber publication); the app ingests them through the hot folder's verified ingest with the next-capture settings, after writing what the photo is given next to it, so a crash at any point leaves either a quarantined partial download (never ingested) or a complete one that is ingested exactly once. No file on a memory card is ever deleted. A camera that keeps tethered photos in a USB transfer queue until the computer frees them (Fujifilm in USB tether mode; it stops shooting when the queue is full) gets each photo freed from that queue only after the app has verified and committed it to the library (on by default as in Capture One, the user can turn it off in the tether panel; a GFX 50R writes no card copy in this mode, so the library copy can be the only one; an X-H2S keeps its card copy, checked on the body); elsewhere this is a no-op (user decision 2026-10-19, as Capture One does). Photos already in that queue when the camera is connected (taken while no computer took them, or left by an earlier connection) are fetched after every connect and reconnect, as Capture One fetches them when it starts (user decision 2026-10-26): the helper lists the queue read-only (libgphoto2's file list: PTP GetObjectHandles and GetObjectInfo), downloads one per turn of its loop through the same crash-safe transfer folder, so requests and new shots are served while it drains, and the app takes them in like any photo; each is freed only after its verified commit and only with freeing on. One that fails stays on the camera and is reported. A file reported later under a queued photo's name is fetched as that photo until it is in the transfer folder, and one of such a name that cannot be downloaded answers no app shot (it cannot be told from the old photo); if the queue cannot be listed, the connection fires no shot (a new photo could not be told from the queued ones) and says so. A queued photo fetched again by a later connection (freeing off, or not freed yet) is recognised by the ingest's content check and not taken in twice. Which camera operation is used (trigger and wait for the file, the blocking capture, live view) follows the driver's result codes, never a list of bodies — libgphoto2's own model table included, which lists bodies its driver fires as unable to capture; a shot that does not arrive is reported, never fired again. A camera set to keep its photos only in its memory (a capture target without the card) lets go of a photo once it has been transferred — libgphoto2 acknowledges a Canon EOS transfer while reading the event, before the helper has written the file — so a helper crash in that moment would lose it: so a connection never keeps photos only in the camera's memory: at the connect Save to goes to an option with the card where the camera offers one (else the camera is not opened), switching it to memory only is refused, and a camera found keeping photos only in its memory later (card taken out, changed on the body; checked before every shot and every 2 s) is neither fired nor read for the rest of the connection. Canon cameras are not offered yet (user decision 2026-10-19): no Canon body was tested, libgphoto2's EOS trigger discards the events it collected before firing (a photo's report can be lost), and its Save to shows a preference while the camera falls back to its memory without a card. (A Fujifilm transfer queue is safe: its photos are freed only after the commit.)

libgphoto2 and libltdl (and libusb on Linux) are linked dynamically into the helper alone and shipped as separate libraries, built from pinned upstream sources with only the PTP camera driver and one port driver (`scripts/tether/build_libgphoto2.sh`; no network port driver).

**macOS port driver (2026-10-19).** macOS's camera service (`ptpcamerad`) claims every PTP camera on USB; libusb cannot claim it then, and ending that service is not ours to do (it also left a body stuck after a replug). On macOS libgphoto2 therefore talks through our port driver `icc` (`crates/tether/macos/icc_port.m`): it presents each ImageCaptureCore camera that accepts PTP commands as a USB port and carries libgphoto2's PTP transactions over `ICCameraDevice requestSendPTPCommand:outData:completion:` and its PTP events — the system path Capture One uses. libgphoto2's PTP driver keeps all vendor protocol logic. ImageCaptureCore delivers cameras only to a running NSApplication, so the helper runs one on its main thread (no Dock icon) and serves requests on another; macOS asks the user once to allow the helper access to removable media. The helper builds without camera support (`gphoto2` feature off) everywhere else, so CI and contributors need no libgphoto2; the scripted mock camera (`--mock`) drives the tests and the UI without a camera.

**Exposures (2026-10-20).** The helper numbers each exposure per connection (`Captured::exposure`): the RAW and JPEG of one exposure share the number and answer one app request, also when they arrive interleaved with other exposures' files, however late. A file goes to the newest exposure of its name (without the extension) that has not given its kind yet. libgphoto2 gives no exposure identity, so with a reused file name (the camera's numbering wrapped or was reset) the pairing can be ambiguous: A.RAW, A.RAW, A.JPG, A.JPG may be two RAW+JPEG exposures or two RAW-only and two JPEG-only ones, and A.RAW; A.RAW+A.JPG; A.JPG has the same problem. Such a file is marked `ambiguous`, and the guided camera test reports its step as inconclusive, never as pass or fail.

**Consequences.** A crash or hang ends only the helper; the next command starts a new one and the transfer folder is recovered. Requests cost one pipe round trip plus up to one event poll (20 ms). The bundles carry four LGPL libraries and two driver modules, and every release must offer their sources from the same place (THIRD_PARTY_NOTICES). A direct protocol path for bodies where libgphoto2 is measured below Capture One (G48) would be another backend behind the same helper protocol.
