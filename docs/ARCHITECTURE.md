# Architecture
## Implemented baseline and target
The desktop adapter lives in `src-tauri`, using the attributed RapidRAW renderer and React workspace in `src`. Native wgpu presents under the transparent webview. Renderer commands and small thumbnails cross IPC; native Develop output stays on GPU.
New Rust workspace crates isolate data and file safety. `catalog`: migrations, session/catalog manifest, relative paths, identity, metadata and recipe history. `metadata`: atomic sidecar IO and shared recipe provenance predicates (`provenance`, consumed by the renderer, export and catalog). `naming`: strict templates. `ingest`: streamed verified no-clobber copying. `cli`: desktop-independent session operations and measured benchmarks.
Engine layers are extracted from the adapter per ADR 0009, dependencies pointing downwards only and checked by `scripts/check_layering.sh` in CI. Extracted, lowest first: `runtime` (opt-in stage timing, allocator release) and `rawdecode` (RAW bytes to oriented linear RGB: rawler front end, CPU and GPU X-Trans demosaic, DNG opcodes, highlight reconstruction (colour ratios inside large partly clipped areas from `renderVersion` 9), hot pixels, unbiased shadow blacks of `renderVersion` 8 (`black_bias`), maker-note capture data, camera colour and per-unit calibration). `engine` (the develop model and its JSON-to-uniform translation, geometry, CPU detail stages, scopes, auto analysis, camera defaults and DCP profiles, looks and colour tools, Lensfun parsing and lens maths, the edge-fringe pass (CPU versions 1–4; version 5 on the GPU in `edge_fringe/gpu.rs` with its WGSL, using the device the app or `GpuContext::headless` registers, as rawdecode's GPU demosaic does), the geometry warp of `renderVersion` 7 on that device (`warp_gpu.rs`), spot removal, mask layer definitions; `masks::paste_layers` and `pending_detections`: the copy/sync layer rule and the export refusal of AI selections not detected yet, ADR 0015). The adapter re-exports them under their former module names and keeps their Tauri commands in thin modules of the same name. `engine` also holds mask rasterisation and the recipe hashes. `gpu` (the wgpu pipeline, shaders, readback and native display presentation onto a surface the app creates; GPU equivalence tests). `export` (render pipeline with an explicit `RenderEnv`, resize/border/watermark, encoders, EXIF/XMP export metadata, no-clobber output, single-file export used by `rawtonic export`, and the persistent export queue's state in `queue`: jobs and their photos with state, output, error and timing; pause, cancel, resume, retry, recovery after a crash). `merge` (HDR, panorama and focus stack on scene-linear base images, written as 16-bit float linear DNGs with the source's colour matrices, As Shot balance, EXIF and an equivalent baseline, so a merge develops like a RAW; used by the app's merge dialog and `rawtonic merge`). `faces` (face detection, landmarks and parsing on ONNX Runtime, and People-mask rasterisation; the app downloads its models and stores the masks as bitmaps). Still in the adapter: the window surface and the processor/cache slots in `AppState`, the export queue's runner (`export_queue`: one job at a time, per-job pause/cancel, `export-item-progress` stage events incl. AI Denoise tiles through `MosaicDenoise::with_progress`, read by the studio's queue panel `StudioExportQueue`; a job carries each photo's recipe and embedded metadata, read once at submission through the library it was submitted from (`export_processing::pin_photos`), and its runner reads no library), editor-sidecar and session catalog reads, the AI models, `tether`, file management and the session bridge. The actual pipeline is not yet the requested ProPhoto/DCP pipeline. Working values are linear sRGB primaries with a ProPhoto gamut (negative channels beyond sRGB); every output (sRGB, Display P3, Adobe RGB, ProPhoto exports, the Display P3 view on macOS) is that one rendering clipped at the end (ADR 0010).
## Storage
Opening a session or catalog requires SQLite WAL mode on every platform. Existing WAL mode is read before any transition is requested; if WAL cannot be enabled, opening fails with a database configuration error rather than silently proceeding in another journal mode.
Sessions contain session.json, session.sqlite (WAL), Capture, Selects, Output, Trash, masks and disposable .cache. Asset references in a session are relative, validated against traversal and symlinks. Catalog bundles use catalog.sqlite and absolute external roots. One schema supports both modes. SQLite metadata and versioned recipes are authoritative for managed assets. Recipe strings of 16 KB and more (AI mask bitmaps, Relight analyses) are stored once by SHA-256 in `recipe_blobs` and referenced from every history step (`rawtonic-blob:sha256:<hex>`, schema 7); reads restore them, removals prune unreferenced ones. Legacy sidecars form an explicit adapter bridge during migration. Nothing removes an asset because its file is gone: it is marked missing (offline), keeps its edits, metadata and albums, stays listed in its folder and albums and in the Missing Photographs view, and opens on its previews; edits made offline go to SQLite only and the derived sidecars follow when it comes back. External roots record their volume (UUID, name, mount point; `crates/catalog/src/volume.rs`), so a disconnected drive is named and a drive mounted elsewhere is followed. Volume kind (startup/local/removable/network) and configured roots without photographs keep their last observed drive in SQLite (schema 15, `folder_root_volumes`); the Folders panel orders the startup disk first and marks network shares. Relinking (one photograph with its folder neighbours, or a folder) accepts a file only with the registered size and content fingerprint and changes only database rows, in one transaction. Adding photographs (`crates/catalog/src/add.rs`) is walk → plan → insert: callers find the files, `plan_add` reads and validates what each brings (editor sidecar, else XMP), and `insert_planned` stores all of them with recipe and metadata in one transaction, into the current import batch (`import_batches`, `asset_imports`; the newest is Previous Import). Synchronize Folder (`crates/catalog/src/folder_sync.rs`, app glue `src-tauri/src/folder_sync.rs`) is scan → review → apply: a read-only, cancellable scan lists a folder (or every root), matches files no asset references against missing and present assets by size and sampled fingerprint, and proves matches with the full SHA-256 recorded per asset (`assets.sha256`, `checksum.rs`: written by verified ingest and a throttled background pass, since a missing file cannot be hashed any more). It classifies verified and probable moves, copies, contested files, new files, removed and unavailable (disconnected drive: never moved or removed) photographs. A photograph is only removed when its folder was listed and its library folder (the library's own, or a catalog folder it is in) is there and not empty; below a catalog folder that is not there (a drive or share without a volume identity — Windows, SMB/NAS — looks just like that) it is unavailable, and apply refuses its removal too. Apply checks every accepted action against disk and database again, commits moves and removals in one transaction (the asset id stays, so edits, metadata, versions and albums follow) and adds new files through `add_files` as a "sync" batch; when adding fails, the committed moves and removals are still reported (and followed by previews), the files as skipped with `addError`. Opening a library follows verified moves only among the new files of its own folder (`scan_files_sync`: no folder listed, only files matching an asset by size and fingerprint hashed). Files are never moved, modified or deleted. A library's hot folder is kept in it (`hot_folder`, `hot_folder_files`, schema 8; `crates/catalog/src/hot_folder.rs`): the watched folder, template, subfolder option and next-capture settings, the last capture, and the files taken (path relative to the watched folder, size, modification time), so watching resumes when the library opens again and files that arrived meanwhile are taken once without hashing the earlier ones again; transferred or restored copies drop it.
Preferences → Storage (`src-tauri/src/storage.rs`, `storage_fs.rs`) inventories logical file bytes in blocking workers. Each category walk has a 2 s budget (partial totals are labelled), is cancellable, and is reused for 5 s. The cache root owns thumbnails, previews outside libraries, metadata reads and model first-run markers; exact app-data subdirectories own denoise results and downloaded models, the app log directory owns logs, and only the active library's `.cache` is eligible there. Clear validates these fixed roots, refuses descendant links, keeps the active log, staging/recent files and active readers, and leaves directory structure in place. Unix removal is anchored with directory descriptors; the Windows implementation pins ancestors against renames and refuses reparse points; native Windows execution remains unqualified. Model removal needs confirmation and runs before model loading at the next launch; installed execution-provider plug-ins are preserved, and system Core ML caches are read-only. Thumbnail and denoise-result limits (2/5 decimal GB by default, 0 unlimited) are applied once per minute and on preference changes; active or recently used entries may keep a cache above its limit temporarily. Standard previews retain their existing LRU/offline protection and separate 1:1 expiry policy. Successful webview thumbnail loads (including the decoded-preview path) refresh cache-family last-use timestamps through one batched IPC accepting only validated opaque cache keys. Preview clearing and size limits live only in Storage; Preview settings link there, and the all/1:1 clear choices share one confirmed native action. Cached thumbnail images recover an expired asset URL on demand without replacing the viewport queue; decoder work for recovery is admitted through one additional slot before entering the blocking pool; the shared file URLs are refreshed after recovery, and failed recovery shows a placeholder with no retry loop. Vanished staging files are skipped while scanning; an undeletable file is kept while eviction continues with other candidates. Staging files are counted with their owning cache or model directory; there is no separate app scratch tree. Decoded-image storage is RAM, shown separately with its existing count limit.

## File safety
Copy into a unique temporary file beside the destination, flush, compare source and destination SHA-256, publish with no-clobber atomic persistence. Never overwrite on collision. Source files are opened read-only. Metadata writes are atomic. Unsupported destructive operations must fail clearly rather than fall back to deletion.
## Concurrency
Native renderer retains cancellation generations, coalescing, workers and bounded preview strategies. Catalog transactions run in blocking workers for IPC; no SQLite connection is shared between threads. Ingest is background work; each copy ingest is a job in the library database with explicit item states (pending, copying with its planned copies, done, failed), resumed when the library is opened again (ADR 0013). Every write of a photograph's recipe, sidecar or XMP from the webview (editor autosave, batch paste/preset/sync/reset, lens and Auto corrections, recipe undo/redo, ratings, labels, flags, keywords, EXIF and text fields, snapshots) goes through that photograph's one write queue (`src/utils/photoWrites.ts`, keyed by the file, so virtual copies share it): a write starts after every write submitted before it for any of its photographs, its dependencies taken at submission, and each settled write, failed or partly failed, is announced once (`PHOTO_WRITES_SETTLED`, which the session bar's XMP count listens to). The backend keeps each sidecar read-modify-write atomic (`sidecar_field_edit`); the order is the webview's.
Background work and its outcomes are reported in one place, the activity centre in the session bar beside the library name (`src/store/useActivityStore.ts`, `src/components/activity/ActivityCentre.tsx`, ⌥⌘A / Ctrl+Alt+A, View → Activity…): running tasks with progress and Cancel, recent results (they expire after 15 minutes) and what needs attention (warnings and failures with their actions, kept until resolved or dismissed). `src/activity/bridges.ts` follows the paths with their own state (export queue, AI tasks and AI Denoise, model downloads, indexing, batch commands, the photo write queue); everything else calls `notify` (`src/activity/notify.ts`, shaped like the toast API): `error`/`warn` become entries, `success`/`info` confirm the user's own action with a ~3 s toast and are logged under Done. Only `notify` and `AppNotices` use react-toastify (`src/activity/noToastFailures.test.ts`); background failures never open a dialog.

## Release gates
Target hardware and fixtures are named in the maintainers' benchmark notes. No budget is green without measured evidence. Core tests, UI type checks, production bundle, native compilation and real sample render are separate gates.

**Desktop adapter (`src-tauri/`, crate `rawtonic-app`, lib `rapidraw_lib`)** — Tauri commands, `AppState`, image loading/caches, file management, export, AI, tether, culling, merge/collage glue and the thin glue modules over the engine crates. `export_processing`, `image_loader`, `exif_processing` and the other same-named modules are now thin glue over the engine/export crates; still inherited and Tauri-bound: file_management, ai_*, inpainting, tagging, camera_tethering. ADR 0009 moves AI/tether only when a consumer outside the app needs them, by its move-don't-rewrite method and byte-identical-export gate. Moved modules stay reachable under their old `crate::<module>` names through those glue modules or a `use rawtonic_…::{…}` line in `lib.rs`. Don't add empty crates pretending a separation exists. `lib.rs` is wiring only: module declarations, `run()` and `generate_handler!`; the Develop source/preview pipeline lives in `editor_preview.rs`, start-up services in `startup.rs`, merges in `merges.rs` over rawtonic-merge, Open With / Edit With in `open_with.rs` (programs from LaunchServices on macOS, disabled elsewhere; Edit With queues one export per photo through the export queue, snapshotted at the click like any queued export, to `NAME_edit.<ext>` beside the original, registers each render stacked with its original via `catalog::derived` (`assets.stack` = the original's id) and watches it, so a save in the other program refreshes its thumbnail). There are no crate-root re-exports: import from the owning module (`crate::app_state::AppState`, `crate::app_settings::load_settings`). `file_management.rs` re-exports its submodules (`file_management/{listing,folders,albums,thumbnails,edits,operations,presets,xmp_sync}.rs`). `session_bridge.rs` is the transitional adapter between the inherited editor (which uses `filename.ext.rrdata` sidecars) and the portable SQLite session; it also writes standard metadata + recipe to `filename.xmp`. The library tracks each sidecar's state (`metadata.xmp_status`: synced, pending, conflict, with the digest it last wrote or read); `catalog::xmp_state` says why each unsynced one is not written (`XmpProblem`, one check for the list and Try again `write_pending_xmp`), `catalog::xmp_review` lists them and resolves sidecars changed elsewhere (`keep_library_xmp`, `use_xmp` with `undo_use_xmp`), and `src-tauri/src/xmp_review.rs` serves the session bar's XMP status panel (`SessionXmpStatus`; Use XMP is a step of `utils/appUndo`, all of it on the photo write queue). Sidecars changed elsewhere while in sync are found without a write (`Library::check_xmp_sidecars` reads only new or changed ones, by size and modification time, then `mark_changed_elsewhere` under the write lock; `session_xmp_check`, run by `utils/xmpCheck.ts` when a library opens, the app is back in front or a folder is shown; no file watching or polling). Metadata writes never change the look: `Library::adopt_editor_sidecar` takes an edit that is only in a photo's `.rrdata` into the library before `set_metadata`, flags, Use XMP and Keep library.
