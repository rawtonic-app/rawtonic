# Architecture
## Implemented baseline and target
The desktop adapter lives in `src-tauri`, using the attributed RapidRAW renderer and React workspace in `src`. Native wgpu presents under the transparent webview. Renderer commands and small thumbnails cross IPC; native Develop output stays on GPU.
New Rust workspace crates isolate data and file safety. `catalog`: migrations, session/catalog manifest, relative paths, identity, metadata and recipe history. `metadata`: atomic sidecar IO. `naming`: strict templates. `ingest`: streamed verified no-clobber copying. `cli`: desktop-independent session operations and measured benchmarks.
Engine layers are extracted from the adapter per ADR 0009, dependencies pointing downwards only and checked by `scripts/check_layering.sh` in CI. Extracted, lowest first: `runtime` (opt-in stage timing, allocator release) and `rawdecode` (RAW bytes to oriented linear RGB: rawler front end, CPU and GPU X-Trans demosaic, DNG opcodes, highlight reconstruction, hot pixels, maker-note capture data, camera colour and per-unit calibration). `engine` (the develop model and its JSON-to-uniform translation, geometry, CPU detail stages, scopes, auto analysis, camera defaults and DCP profiles, looks and colour tools, Lensfun parsing and lens maths, spot removal, mask layer definitions). The adapter re-exports them under their former module names and keeps their Tauri commands in thin modules of the same name. `engine` also holds mask rasterisation and the recipe hashes. `gpu` (the wgpu pipeline, shaders, readback and native display presentation onto a surface the app creates; GPU equivalence tests). `export` (render pipeline with an explicit `RenderEnv`, resize/border/watermark, encoders, EXIF/XMP export metadata, no-clobber output, single-file export used by `rawtonic export`). `merge` (HDR, panorama and focus stack on scene-linear base images, written as 16-bit float linear DNGs with the source's colour matrices, As Shot balance, EXIF and an equivalent baseline, so a merge develops like a RAW; used by the app's merge dialog and `rawtonic merge`). `faces` (face detection, landmarks and parsing on ONNX Runtime, and People-mask rasterisation; the app downloads its models and stores the masks as bitmaps). Still in the adapter: the window surface and the processor/cache slots in `AppState`, the export queue, editor-sidecar and session catalog reads, the AI models, `tether`, file management and the session bridge. The actual pipeline is not yet the requested ProPhoto/DCP pipeline. Working values are linear sRGB primaries with a ProPhoto gamut (negative channels beyond sRGB); every output (sRGB, Display P3, Adobe RGB, ProPhoto exports, the Display P3 view on macOS) is that one rendering clipped at the end (ADR 0010).
## Storage
Sessions contain session.json, session.sqlite (WAL), Capture, Selects, Output, Trash, masks and disposable .cache. Asset references in a session are relative, validated against traversal and symlinks. Catalog bundles use catalog.sqlite and absolute external roots. One schema supports both modes. SQLite metadata and versioned recipes are authoritative for managed assets. Recipe strings of 16 KB and more (AI mask bitmaps, Relight analyses) are stored once by SHA-256 in `recipe_blobs` and referenced from every history step (`rawtonic-blob:sha256:<hex>`, schema 7); reads restore them, removals prune unreferenced ones. Legacy sidecars form an explicit adapter bridge during migration. Nothing removes an asset because its file is gone: it is marked missing (offline), keeps its edits, metadata and albums, stays listed in its folder and albums and in the Missing Photographs view, and opens on its previews; edits made offline go to SQLite only and the derived sidecars follow when it comes back. External roots record their volume (UUID, name, mount point; `crates/catalog/src/volume.rs`), so a disconnected drive is named and a drive mounted elsewhere is followed. Relinking (one photograph with its folder neighbours, or a folder) accepts a file only with the registered size and content fingerprint and changes only database rows, in one transaction. Adding photographs (`crates/catalog/src/add.rs`) is walk → plan → insert: callers find the files, `plan_add` reads and validates what each brings (editor sidecar, else XMP), and `insert_planned` stores all of them with recipe and metadata in one transaction, into the current import batch (`import_batches`, `asset_imports`; the newest is Previous Import). Synchronize Folder (`crates/catalog/src/folder_sync.rs`, app glue `src-tauri/src/folder_sync.rs`) is scan → review → apply: a read-only, cancellable scan lists a folder (or every root), matches files no asset references against missing and present assets by size and sampled fingerprint, and proves matches with the full SHA-256 recorded per asset (`assets.sha256`, `checksum.rs`: written by verified ingest and a throttled background pass, since a missing file cannot be hashed any more). It classifies verified and probable moves, copies, contested files, new files, removed and unavailable (disconnected drive: never moved or removed) photographs. A photograph is only removed when its folder was listed and its library folder (the library's own, or a catalog folder it is in) is there and not empty; below a catalog folder that is not there (a drive or share without a volume identity — Windows, SMB/NAS — looks just like that) it is unavailable, and apply refuses its removal too. Apply checks every accepted action against disk and database again, commits moves and removals in one transaction (the asset id stays, so edits, metadata, versions and albums follow) and adds new files through `add_files` as a "sync" batch; when adding fails, the committed moves and removals are still reported (and followed by previews), the files as skipped with `addError`. Opening a library follows verified moves only among the new files of its own folder (`scan_files_sync`: no folder listed, only files matching an asset by size and fingerprint hashed). Files are never moved, modified or deleted. A library's hot folder is kept in it (`hot_folder`, `hot_folder_files`, schema 8; `crates/catalog/src/hot_folder.rs`): the watched folder, template, subfolder option and next-capture settings, the last capture, and the files taken (path relative to the watched folder, size, modification time), so watching resumes when the library opens again and files that arrived meanwhile are taken once without hashing the earlier ones again; transferred or restored copies drop it.
## File safety
Copy into a unique temporary file beside the destination, flush, compare source and destination SHA-256, publish with no-clobber atomic persistence. Never overwrite on collision. Source files are opened read-only. Metadata writes are atomic. Unsupported destructive operations must fail clearly rather than fall back to deletion.
## Concurrency
Native renderer retains cancellation generations, coalescing, workers and bounded preview strategies. Catalog transactions run in blocking workers for IPC; no SQLite connection is shared between threads. Ingest is background work; each copy ingest is a job in the library database with explicit item states (pending, copying with its planned copies, done, failed), resumed when the library is opened again (ADR 0013).
## Release gates
Target hardware and fixtures are named in the maintainers' benchmark notes. No budget is green without measured evidence. Core tests, UI type checks, production bundle, native compilation and real sample render are separate gates.
## Crate map (where code lives)
Read the part for the crate you change. Moved verbatim from AGENTS.md (2026-10-17) so agents load it only when needed.

**Core crates (`crates/`)** — new, standalone, desktop-independent, with real tests:
- `catalog` — SQLite schema/migrations, session and catalog modes (one schema), relative-path validation (traversal/symlinks), asset identity, metadata, versioned recipe history. SQLite is authoritative for managed assets.
- `fileops` — journaled, undoable and redoable rename/move/trash (validated plan, no-clobber renames, rollback, crash recovery; redo re-validates; the system Trash is a trait the app implements) and `purge`, the only deletion: emptying one real folder (a session's `Trash/`) — entries set aside first, committed, then deleted without following links; not undoable, it ends Undo for earlier operations. App glue: `src-tauri/src/file_operations.rs`.
- `metadata` — atomic XMP sidecar IO; `no_clobber::persist` publishes a finished temporary file under a new name, never replacing one (export outputs, ingest copies, generated images; tether transfer slots use `persist_in_own_folder`), with an O_EXCL copy where the volume has no exclusive rename or hard links (exFAT/FAT; the copy's short non-atomic window is documented there). `naming` — strict filename templates. `ingest` — streamed copy to temp file, SHA-256 verify both sides, no-clobber publish, optional backup destination, cancellation; card XMP sidecars matched ignoring letter case; RAW+JPEG pairs imported as one photograph with the JPEG as its companion (ADR 0013; `catalog::companion`: `assets.raw_jpeg_pair`, never registered again, left out of listings by `session_bridge::companions_in_folder`, moved and trashed with its RAW by `file_operations::associated_files`); every copy ingest is a resumable job (`ingest::queue`, `catalog::ingest_jobs`: `tasks` + `ingest_items`, planned copies recorded before copying; app glue `session_ingest_jobs`/`_resume`/`_forget`).
- `denoise` — AI Denoise: Nonlocal MatchFilter on the Bayer mosaic (Core ML on macOS, ONNX Runtime elsewhere), blind noise estimate (scaled by `MosaicDenoise::noise_scale`), tiles of the model's input size, a content-keyed f16 cache; plugs into rawdecode's `mosaic_denoise` hook (before highlight reconstruction and demosaicing). App glue `src-tauri/src/ai_denoise.rs` (one denoiser per model: versions 1–2 the first Core ML package, version 3 the mixed-precision 640 px one; no fallback, so a recipe always renders with its version's model); the recipe's `aiDenoise` (0–100) and `aiDenoiseVersion` decide (`rawtonic_engine::image_loader::ai_denoise_settings`), Develop re-develops via `apply_ai_denoise`. Its `coreml::CoreMlModel` (compile once to `.mlmodelc`, one float input/output) also runs the app's BiRefNet Subject model on macOS (`ai_processing::SubjectModel`, ONNX fallback; masks computed ahead when the masking tools open, `precompute_ai_foreground_mask`).
- `faces` — faces for People masks and the face retouch: YuNet detection (two passes), MediaPipe Face Mesh V2 landmarks, MediaPipe multiclass parsing per face and of the whole photo, and `part_mask` (skin, hair, clothes, eyes, brows, lips, teeth, entire person; everyone or one person). Models from the pack (`scripts/models/export_faces.py`, docs/MODELS.md); app glue `src-tauri/src/ai_faces.rs` (`detect_people`, `generate_ai_people_mask`, the open photo's analysis cached in `AppState.faces`); the mask is stored as an `ai-people` bitmap. `retouch` makes the face retouch's per-face data (crop, skin and under-eye weights, blemishes with prominence) for `analyze_face_retouch`; the engine's `face_retouch` renders it (blemishes healed without a source, even skin/texture, dark circles, shine) after spot removal. Ignored tests `crates/faces/tests/real_photos.rs` (`FACE_MODELS`, `FACE_PHOTOS`, `FACE_OUT`, `ORT_DYLIB_PATH`) write part overlays and `retouch_photos.rs` blemish overlays; `cargo test -p rawtonic-app --release --lib renders_face_retouch -- --ignored` renders before/after crops (`FACE_SETTINGS`).
- `onnx` — every ONNX model loads through `rawtonic_onnx::Model`: GPU plugin providers (CUDA if installed, WebGPU on Windows/Linux) checked once against the CPU, CPU fallback, per-model exceptions, preference `aiGpu` (ADR 0011). `rawtonic ai-bench` times and compares providers.
- `tether` — tethered shooting (ADR 0012): the helper program `rawtonic-tether` (libgphoto2 behind the `gphoto2` feature, dynamically linked, never in the app; `--mock` scripted camera; `probe` and `version` commands), its protocol and framing, the crash-safe transfer folder (`staging`: `<session>/.tether/incoming`, partial downloads quarantined in `incomplete/`) and the app's client (`client`: request timeouts, helper death detected by exit, not only by EOF). App glue `src-tauri/src/camera_tethering.rs`: starts the helper, ingests its photos through `hot_folder::ingest_capture` with a transfer record written first, `tether-*` events; UI `src/components/session/TetherPanel.tsx`, its guided camera test `TetherCameraTest.tsx` (anonymous report: `cameraTest.ts`) and the compatibility list `tetherCameras.json` (docs/TETHER_CAMERAS.md). Packaging: `scripts/tether/build_libgphoto2.sh`, `bundle_helper.sh`.
- `cli` — the `rawtonic` binary over the above, plus measured benchmarks (`decode` times rawdecode without the app).
- `merge` — photo merges on scene-linear frames (`frame`: base images without colour NR/sharpening, `load_corrected` for lens-corrected, rebalanced frames): `hdr` (Poisson-optimal merge, alignment, deghosting), `panorama` (own keypoints, bundle adjustment, projections, seams cut where frames agree, two-band blending, boundary warp/crop applied after the stitch), `hdr_panorama` (brackets grouped per position → HDR → stitch), `focus_stack` (the moved stacker + `align`/`planes`), and `dng` writing the result as a 16-bit float linear DNG that develops like the source RAW (matrices, As Shot, EXIF, `dng_baseline_equivalent`; lens data in the starting `.rrdata` via `initial_adjustments`). App glue `src-tauri/src/merges.rs` (`merge_photos`/`save_merge`, one `MergeModal`); collage rendering `src-tauri/src/collage.rs`. CLI `rawtonic merge {hdr,pano,hdrpano,focus,single} … [--auto-settings]`; synthetic test sets and comparisons in `crates/merge/examples/` (notes: reference/merges.md).
- Engine layers extracted from the adapter (ADR 0009), lowest first: `runtime` (stage timing behind `performance-profiling`, allocator release); `rawdecode` (raw_processing, demosaic, gpu_demosaic, DNG opcodes/colour, capture_info, camera colour/exposure tables); `engine` (image_processing core = adjustment model/geometry/detail/scopes, baseline_exposure, auto_adjust, camera_profile, looks/colour tools, lens_correction + embedded_lens maths, lens_recipe (a recipe's lens parameters: `lensProfileFor` stamp, save-time `LensLookup`, `resolve_unresolved` before rendering), spot_removal, face_retouch, mask_generation rasterisation + masks definitions + mask_parameters (brush strokes a preview request refers to by token), cache_utils hashes, lut); `gpu` (gpu_processing: GpuProcessor, shader variants + WGSL in `crates/gpu/src/shaders/`, readback, WgpuDisplay presentation, `GpuContext::headless`, GPU equivalence tests); `export` (export settings/geometry/encoders, render pipeline with `RenderEnv`, exif_processing/tiff_exif/xmp_embed with `export_metadata_with` + `encode_with_metadata`, `sidecars` (virtual paths, `.rrdata` reading, library walk, export naming), `output::write_new_output`, `file_export::FileExporter`). Engine also holds image_loader's decode path (`load_base_image` + `BaseImageOptions`), adjustment_utils and the LUT parsers. `scripts/check_layering.sh` (CI) fails if any of these crates reaches Tauri.
- Where to edit: develop logic → the crate (`crates/engine`, `crates/rawdecode`, `crates/gpu`); a Tauri command or `AppState` access for it → the same-named thin module in `src-tauri/src` (e.g. `src-tauri/src/camera_profile.rs` = `pub use rawtonic_engine::camera_profile::*` + commands; `src-tauri/src/gpu_processing.rs` = window surface, the processor/image cache in `AppState`, render wrappers taking `tauri::State`). Engine/GPU functions take data (device, caches, images), never `AppState`. Test-only helpers for another crate's tests go behind a `test-support` feature.

**Desktop adapter (`src-tauri/`, crate `rawtonic-app`, lib `rapidraw_lib`)** — Tauri commands, `AppState`, image loading/caches, file management, export, AI, tether, culling, merge/collage glue and the thin glue modules over the engine crates. `export_processing`, `image_loader`, `exif_processing` and the other same-named modules are now thin glue over the engine/export crates; still inherited and Tauri-bound: file_management, ai_*, inpainting, tagging, camera_tethering. ADR 0009 moves AI/tether only when a consumer outside the app needs them, by its move-don't-rewrite method and byte-identical-export gate. Moved modules stay reachable under their old `crate::<module>` names through those glue modules or a `use rawtonic_…::{…}` line in `lib.rs`. Don't add empty crates pretending a separation exists. `lib.rs` is wiring only: module declarations, `run()` and `generate_handler!`; the Develop source/preview pipeline lives in `editor_preview.rs`, start-up services in `startup.rs`, merges in `merges.rs` over rawtonic-merge. There are no crate-root re-exports: import from the owning module (`crate::app_state::AppState`, `crate::app_settings::load_settings`). `file_management.rs` re-exports its submodules (`file_management/{listing,folders,albums,thumbnails,edits,operations,presets,xmp_sync}.rs`). `session_bridge.rs` is the transitional adapter between the inherited editor (which uses `filename.ext.rrdata` sidecars) and the portable SQLite session; it also writes standard metadata + recipe to `filename.xmp`.
