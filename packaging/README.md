# Development packaging
`npm run tauri -- build` produces DMG/app on macOS and AppImage/deb on Linux when the native SDK is installed. This Mac can qualify only Apple Silicon. No signing/notarization credentials are configured. Do not label unsigned development artifacts production-ready.

macOS (2026-10-08): `npm run package:mac` builds `Rawtonic.app` and `Rawtonic_<version>_aarch64.dmg` in `target/release/bundle/`. It sets `CI=true`, which makes Tauri's DMG script skip the Finder window styling (that AppleScript needs Automation permission for Finder and fails without it, which made a plain `tauri build` stop at the DMG). The bundle is signed ad hoc as a whole (`signingIdentity: "-"` in `src-tauri/tauri.macos.conf.json`, hardened runtime): `codesign --verify --deep --strict` passes and the app starts, renders and exports with it; before, only the binary carried the linker's ad-hoc signature and the bundle failed verification ("code has no resources"). Gatekeeper still refuses it on other Macs until it is signed with a Developer ID and notarized — that needs the owner's Apple certificate. The hardened runtime's library validation refused the bundled ONNX Runtime (Microsoft's build, signed separately; an ad-hoc signature never satisfies it), so every AI tool failed in bundled builds between 2026-10-08 (signing) and the same day's fix: `src-tauri/Entitlements.plist` grants `com.apple.security.cs.disable-library-validation`, which also works for a later Developer ID build.

Flatpak and AUR files are explicit skeletons. Flatpak needs offline vendoring and resource installation; AUR needs final resource layout and a public source URL. CI (`.github/workflows/ci.yml`) runs on Linux only, after merges into main. Intel macOS has not been run locally.

Linux (2026-10-11): the source tree was built over SSH on CachyOS x86_64 (kernel 7.2.3-1-cachyos, Rust 1.98.1, Node 22.23.2), with an NVIDIA RTX 3080 and driver 610.57.04. `CI=true npm run tauri -- build --bundles appimage,deb -- --locked` completed the native release build in 10m 03s. Type checking, all 631 frontend tests and the frontend build passed. The Debian package was created (26.64 MiB); installation on Debian/Ubuntu was not tested. This build targets the CachyOS host's libraries, not older distributions.

The initial AppImage exported images successfully but WebKit reported `GStreamer element appsink not found` at window startup: system plugins were installed but missing from the bundle. Enabling `bundle.linux.appimage.bundleMediaFramework` in `src-tauri/tauri.linux.conf.json` and repackaging with `npm run tauri -- bundle --bundles appimage` includes the plugins (189.24 MiB). The corrected AppImage displayed the start screen under Xvfb. PNG, JPEG and TIFF exports of an authored 1536×1024 chart, exposure adjustment, source-hash preservation and output-collision refusal were checked. Those initial checks did not qualify physical-display/Wayland interaction, camera RAW goldens or AI models. The first turbojpeg compilation preceded nasm installation and used no SIMD; this run is not a performance qualification.

Repeat testing found another Linux issue: a successful headless export could exit with SIGSEGV while libc's NVIDIA driver exit handlers raced GPU resource destruction on a Tokio worker. Linux now uses the existing macOS `_exit` path after pending edits and window state have been saved. The final AppImage passed four exports (neutral PNG, adjusted PNG, JPEG and TIFF), ten further PNG process starts/exits, and a collision attempt that returned exit code 1 without changing the existing output. Its window also closed through the title-bar button with exit code 0. The GPU calculated a preview when opening the standalone chart, but visible Develop content was not verified under Xvfb: there was no DRI3 display, and the sessionless view remained on the home screen with software compositing. The baseline Linux workspace suite passed 687 tests with 117 ignored and an explicit RAW-fixture skip; after changes, macOS application tests passed 145 with 38 ignored, and clippy and formatting checks passed.

Linux interaction performance (2026-10-11): Linux keeps its compute-only GPU path and presents JPEG previews through WebKit. The preview encoder now uses libjpeg-turbo directly from RGBA with 4:4:4 colour; Linux x86_64 requires SIMD at build time. The earlier cached turbojpeg build had no NASM compiler even after NASM was installed, so it was explicitly rebuilt. High-quality interactive previews are capped at 1536 px on their long edge, Performance at 1024 px; Full remains uncapped. Release/final frames retain the requested resolution and quality 94. The browser photo container also advertises its transform to the compositor for zoom/pan.

A cloned Sony RAW session with two masks was exercised on physical KDE Wayland, in the same 2648×1446 logical window at scale 2, using synthetic DOM slider input. For 115 fit-view frames the native processing-plus-encoding median fell from 116.52 ms (2560×1707) to 29.42 ms (1536×1024); at 100% zoom it fell from 86.88 ms (113 frames, 2152×1133 ROI) to 18.20 ms (115 frames, 1205×637 ROI). The newer build's interactive IPC median was 33 ms. Both runs refined to 2560×1707 at fit and 3840×2560 at 100%; the original +0.5 EV recipe was restored and the RAW hash stayed unchanged. An additional pan smoke test moved the displayed photo and returned to Fit; compositor screenshots show the image and histogram. Close returned 0. The new build's active five-second frontend frame windows had p95 intervals of 17–20 ms; one window contained an 82 ms frame. These measurements do not include physical-input dispatch or display scanout, and do not establish macOS parity. All 631 frontend tests, the two preview encoder/resolution tests, clippy and formatting passed on macOS; the Linux QA and ordinary release builds compiled the Linux-specific path. Evidence and reproduction scripts are in `artifacts/linux-qa/performance/`.

Linux release AppImage (2026-10-15, 0.1.0-alpha.2): `packaging/linux/build-appimage.sh` builds it in an Ubuntu 22.04 container (`packaging/linux/Dockerfile`, glibc 2.35) with ONNX Runtime 1.30.0 and its WebGPU plugin; a build on the CachyOS host itself would need glibc 2.44 and not start on Ubuntu or Debian. The binary needs at most GLIBC_2.35. linuxdeploy leaves the desktop base libraries out of the AppImage on purpose (fontconfig, fribidi, harfbuzz, libgpg-error, …), so a bare container needs GTK 3 installed to stand in for a desktop. Checked: headless JPEG exports (ARW, RAF, JPEG) under Xvfb with Mesa's software Vulkan in fresh Ubuntu 22.04, Ubuntu 24.04 and Debian 12 containers; on CachyOS (RTX 3080, KDE Wayland) eight of nine test files export headless (the ninth is the unsupported Moto G8 Plus DNG), and a QA-identifier AppImage built the same way opened a session, rendered and adjusted a RAW, ran Relight with a first-time model download (people normals and sky on WebGPU; Subject fell back to the CPU after a WebGPU validation error), exported from the dialog, closed with the window button and kept all originals byte-identical. Later edits render in 11–17 ms at 1536×1024. First start (2026-10-16): with an empty NVIDIA shader cache the first Develop frame comes 9.2–9.4 s after the click (before: 40.5 s, three pipelines compiled one after another), 1.2–1.3 s once the driver cache is warm; the photo's embedded preview shows within a second meanwhile and thumbnails take 2 s.

CI (2026-10-16): `.github/workflows/linux-appimage.yml` builds the same AppImage with `build-appimage.sh` on GitHub's Ubuntu runner (on demand and for `v*` tags), then `packaging/linux/smoke-test.sh` exports three public CC0 raw.pixls.us RAWs (Sony ARW, Nikon NEF, Fujifilm X-Trans RAF, pinned by SHA-256) headless in fresh Ubuntu 22.04, Ubuntu 24.04, Debian 12 and Fedora 42 containers and checks the JPEGs and that the inputs are unchanged. The AppImage and its SHA256SUMS stay a workflow artifact for 14 days; attaching it to a release is a manual step. The smoke script passed with an AppImage of main in all four containers on the CachyOS host. `build-appimage.sh` passes `/dev/fuse` to the container only where it exists (linuxdeploy runs extracted anyway).
